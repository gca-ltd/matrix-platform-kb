# Аудит безопасности — 15 сентября 2026

Проверили 23 живые базы Supabase и интранет (деплой, сертификаты, секреты в бандлах). **Ничего в прод не чинили** — сначала согласовать на дейли.

Ниже без внутренних номеров тикетов: что сломано, кто этим пользуется, что будет, что сделать.

Ключ, о котором речь везде: **публичный ключ приложения** (anon). Он лежит в JavaScript сайта или интранет-приложения. Его может взять любой, кто открыл страницу. С ним ходят в API базы **без логина**.

## Что может сделать посторонний прямо сейчас

### 1. Публичный сайт Венгрии (`sothebys-realty.hu`) — журнал заявок открыт на запись

Есть таблица `conversion_sync_log`: туда пишутся id заявки, id сделки и JSON.  
У таблицы **выключена защита по строкам**. Публичный ключ сайта имеет права читать, создавать, менять и удалять **все** строки.

**Чем грозит:** посетитель сайта (или скрипт) видит, какие заявки ушли в CRM, может подделать или стереть журнал. Это боевой сайт, не стейджинг.

**Как исправить:**
1. Включить защиту по строкам (RLS) на таблице.
2. Разрешить писать только сервисному ключу (Edge Function), не анониму.
3. Снять с анонима INSERT/UPDATE/DELETE (и SELECT, если журнал не должен быть публичным).

### 2. Тот же сайт — любая новая таблица снова откроется сама

Для роли, которая создаёт таблицы, до сих пор стоит правило: «новым таблицам аноним сразу выдаёт полную запись». Из‑за этого пункт 1 и появился после cutover — таблицу добавили, дыра открылась без отдельной ошибки в коде.

**Чем грозит:** следующий релиз Lovable с новой таблицей (лиды, чат, что угодно) снова будет писаться с ключа сайта.

**Как исправить:** один раз снять с анонима права записи **по умолчанию** на будущие таблицы (`ALTER DEFAULT PRIVILEGES … REVOKE INSERT, UPDATE, DELETE FROM anon`). На уже существующие объекты это не влияет. Делать в одном окне с пунктом 1, иначе история повторится.

### 3. Тот же сайт — «счётчик просмотров» шары на самом деле меняет всю шару

Политика называется как счётчик, но разрешает **UPDATE любой строки и любого поля** таблицы `shared_collections` без логина.

**Чем грозит:** можно подменить список объектов в чужой ссылке «поделиться подборкой», испортить или переписать шару.

**Как исправить:** убрать широкую политику UPDATE. Счётчик увеличить отдельной функцией, которая меняет только одно поле. С анонима снять UPDATE. Потребуется правка фронта, если он сейчас делает прямой UPDATE.

### 4. Сайт Кипра — смена ролей без логина

С публичным ключом `sothebysrealty-cyprus.com` можно вызвать функции: назначить роль, снять роль, поменять право, создать пользователя-админа (`update_user_role`, `remove_user_role`, `update_user_permission`, `handle_new_user_admin`).

**Чем грозит:** захват админки сайта Кипра. Не «предупреждение линтера», а конкретный RPC.

**Как исправить:** снять с анонима право EXECUTE на эти функции. Оставить только то, что сайту правда нужно без логина (например счётчик просмотров объекта). SQL на это уже готовили 1 сентября — накатить после согласия.

### 5. HRMS (кадры) — переписать оргструктуру без логина

Таблицы сотрудников для анонима **уже нельзя** ни очистить, ни править напрямую — это закрыли 1 сентября и сегодня подтвердили.

Но остались четыре функции, которые работают **от имени владельца базы** и **не проверяют, кто вошёл**:

- проставить сотрудникам SSO id из Azure;
- скопировать фото из AD;
- заново построить дерево прямых руководителей;
- то же для dotted-line.

Публичный ключ HRMS есть в бандле `intranet…/hrms/`.

**Чем грозит:** кто достучался до API HRMS (интранет, не весь интернет) может перевязать людей к чужим SSO-аккаунтам и переписать, кто чей руководитель. Зарплаты через эти функции не читаются. Клон-песочница HRMS при этом **ещё и** позволяет очищать таблицы — это отдельный риск, если в клоне живые кадры.

**Как исправить:** снять с анонима EXECUTE на эти четыре функции. Вызывать их только из Edge Function с сервисным ключом. То же на песочнице, либо убрать оттуда боевые данные.

### 6. MSA Hungary и ещё семь баз — можно одним ударом очистить таблицы

У анонима и у обычного залогиненного пользователя есть право **TRUNCATE**. Оно **не подчиняется** защите по строкам: политика «видишь только свои сделки» не спасает.

Где так:

| Где | Сколько таблиц можно очистить |
|-----|-------------------------------|
| MSA Hungary (тест, но с CRM-данными) | 66 |
| Песочница MSA Hungary | 66 |
| Песочница HRMS | 42 |
| Analytics + Stardom | 50 |
| Старый Pipeline v1 | 50 |
| Comms (чаты) | 17 |
| Vacations Management | 17 |
| Финансы (FM) | 11 |
| Генератор лидов | 7 |

**Чем грозит:** один запрос опустошает leads / messages / финансовые строки / отпуска. На MSA Hungary это сейчас откладывали из‑за теста — но таблиц стало больше (было 64, стало 66): каждая новая таблица снова получает это право.

**Как исправить:** снять TRUNCATE с анонима и с обычного пользователя; сервисному ключу оставить. Плюс снять то же **по умолчанию** для новых таблиц. На MSA Hungary — после заморозки теста, иначе ломаем стенды.

### 7. Pipeline 2.0 — аноним всё ещё может писать в CRM-таблицы

Очистку таблиц там уже запретили. Но INSERT/UPDATE/DELETE у анонима остались на девяти таблицах, включая сделки, активности и комиссии.

**Чем грозит:** если на таблице широкая политика — с ключа CRM можно создавать/менять сделки. Даже если политика узкая, лишнее право лучше убрать.

**Как исправить:** снять с анонима INSERT/UPDATE/DELETE, как уже сделали на CDL. Не трогать, пока идёт активная разработка — согласовать окно.

### 8. MSA Cyprus — отчёт «расхождения полей» смотрит база как хозяин

Представление `opportunity_field_mismatches` выполняется с правами владельца, не того, кто спросил.

**Чем грозит:** человек с узкими правами может увидеть чужие расхождения по сделкам. Приложение в тесте — править после заморозки: включить «выполнять от имени вызывающего».

### 9. Comms — похожая история с чатами + очистка таблиц

Защиту операционных таблиц (логи, GDPR) включили 25 августа — это не откатилось. Осталось представление `conversations_enriched` с правами владельца и право очистки 17 таблиц (пункт 6).

**Чем грозит:** представление может отдать чужие переписки; TRUNCATE — стереть чаты.

### 10. Вход в SSO / Кипр / HU — не проверяют слитые пароли

HaveIBeenPwned выключен.

**Чем грозит:** сотрудник может поставить пароль из известной утечки. Не дыра «с улицы без пароля», а слабый пароль.

**Как исправить:** тумблер в Dashboard → Auth → Security. Поменяет правила при смене пароля — согласовать с теми, кто логинится.

### 11. Залогиненный на сайте HU может писать в журнал аудита

Политика «сервис пишет аудит» на самом деле разрешена всем, у кого есть обычный логин.

**Чем грозит:** поддельные записи «кто что сделал» в админке сайта.

**Как исправить:** оставить INSERT только сервисному ключу.
