# ADR-063: Storefront partner schema for list-sync listings, interim before CDL MLS 2.1

**Status**: Accepted
**Date**: 2026-10-23
**Scope**: `gca-ltd/matrix-storefront-2.0-hungary` schema `partner` on Supabase `bpaxqtxaysolzaeguwvg`; publisher in `sharpsir-group/dash-matrix-sync`. Related: [ADR-049](ADR-049.md), [ADR-014](ADR-014.md).

## Context

The Hungary website and the Hungary broker app read `public.properties` on the storefront project. That table is also the source of the nightly SharpCRM export (`SELECT *`, no filter). Listings from other SIR offices are available through Anywhere DataSync (list-sync) and already land in the dash-matrix-sync mirror. Putting them in `public.properties` would publish them to every current consumer and would create them in SharpCRM as Hungary inventory.

CDL MLS 2.1 is the intended home (`mls_sources.kind = brand-network` for Dash/DataSync, `kind = external` for a non-SIR developer). It is not what the site reads today. The business needs the listings on the site before that cutover, and the rows have to be removable in one step.

## Decision

1. **Separate schema, same shape.** DataSync listings are stored in `partner.listings` on the storefront database. `public.partner_listings` is an auto-updatable, security-invoker view with the column names of `properties`, plus `country`, `country_code` and `source_code`. Country and source are columns, not tables: one office can cover several countries and one country can have several offices.
2. **The hub writes, the site moderates.** dash-matrix-sync maps the DataSync body and upserts only its own columns, as role `partner_writer`. Visibility, the assigned Hungary agent and Hungarian text overrides are site columns. Postgres grants, not application code, stop the sync from overwriting them. There is no insert or delete for the admin roles. Hiding a row is an update.
3. **Push, with a contract check.** The site does not poll. An hourly job reconciles the active index into the mirror (detail GET only when `lastUpdateOn` moves; a short index does not tombstone) and pushes a pinned cohort. Before writing, the hub compares `partner.contract_version()`, column types and the `property_status` / `property_type` enums. A mismatch writes nothing. A row that leaves the source or the cohort is withdrawn (`removed_at`, status `Withdrawn`) and drops out of the anon view. The id and slug are kept if it returns.
4. **Currency is the source currency.** `price` and `currency` are stored as received. `price_eur` stays null until the business asks for conversion. No change to `public.compute_price_eur`.
5. **Leads outlive the schema.** `property_inquiries.partner_listing_id` and `listing_snapshot` have no foreign key to `partner`. `property_id` stays null. Dropping the schema does not drop the lead.

Lovable builds the UI against the views. It does not migrate `partner`.

## Consequences

- `public.properties`, its triggers, the Hungary MCP, the sitemap and the SharpCRM properties export are unchanged.
- The mirror is shared with SharpCRM. Reconcile is limited to Thailand until tombstoned cards are archived in the CRM. A fresher Thailand mirror also updates CRM cards through the existing hash.
- Removing the feature is `DROP SCHEMA partner CASCADE`, drop the two nullable lead columns, and disable the hub cron.
- When CDL MLS 2.1 is the catalogue the site reads, the hub's mapper and the view's column names are what get repointed. The UI stays on the view.

## Alternatives

- **Rows in `public.properties` with a source column.** Rejected. Every current consumer, including the unfiltered CRM export, would treat them as Hungary inventory.
- **Edge Function on the storefront that pulls the feed.** Rejected. Staging and raw payloads would sit in the website database, and a second ingestion stack would diverge from the hub that already mirrors DataSync.
- **One table per country.** Rejected. DataSync's office and country are not the same axis, and the UI would need a new query per country.
