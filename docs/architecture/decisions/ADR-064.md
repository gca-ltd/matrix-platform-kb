# ADR-064: Seller-side UI ownership — opportunity, inventory item, deal

**Status**: Accepted  
**Date**: 2026-10-27  
**Scope**: Matrix MLS (`gca-ltd/matrix-mls`) seller-side UX and navigation. Related: Matrix MLS repo `docs/business-processes/seller-side-process.md`, [listing-lifecycle.md](../../business-processes/canonical-processes/processes/listing-lifecycle.md) (RESO listing states).

## Context

Matrix MLS already models three objects correctly in the database:

| Object | Role |
|---|---|
| `seller_opportunities` | Seller relationship and mandate (stages Intake → Marketing) |
| `listings` / `developments` | Inventory item — physical record and market state |
| `listing_deals` | One buyer + offer on a property/unit (Negotiation → Closing) |

Listing **StandardStatus** (draft, active, under offer, closed) is separate from **opportunity stage** (board columns). Industry CRMs (Propertybase Listing vs Property, Reapit property vs sales progression) keep the same separation.

Brokers were forced to work in two places: the **seller opportunity workspace** and **inventory record tabs** that duplicated qualification, mandate, and deal workflow. List/Grid also opened the workspace when a linked opportunity existed, while the Board mixed record and workspace targets.

Developer **projects** do not get a second stage pipeline: the developer mandate is one seller opportunity; units are inventory with unit lifecycle statuses and expiring holds.

## Decision

1. **Ownership rule.** Before placing UI or an edit path, classify work:
   - **Seller opportunity** (`/inventory/opportunity/:id`): seller contact, intake, qualification, CMA, commercial terms, confidential price, listing agreement, seller reports, opportunity tasks, hold/lost, history.
   - **Inventory item** (`/inventory/listing/:id`, `/inventory/development/:id`): facts, media, price/publication, listing status, showings, read-only offers list, analysis, generated documents on file, property tasks, activity; for projects, the unit grid.
   - **Deal** (workspace gates Negotiation / Closing): buyer, offer chain, reservation, contract, closing checklist.

   Each datum is edited in exactly one place. Elsewhere: read-only summary + deep link.

2. **Navigation by lens.**
   - **List, Grid, Map** → `recordOpenPath`: open the **record** when a listing/project exists; otherwise the **workspace** (opportunity-only or MSA lead).
   - **Board** → `pipelineOpenPath`: always the **workspace**, at the gate for the card’s column (or `deal` / `closing` for deal cards).

3. **Record chrome.** Listing and project records show a **Seller and mandate** card (stage stepper, status, agreement dates, next action, Open workspace). Tabs that duplicated workspace work (`seller-opportunity`, `qualification`, `mandate`, `contract-status` as seller process) are removed when an opportunity is linked. **Documents** (generated files) stay on the record.

4. **Projects.** One seller opportunity per project mandate; project stays in Marketing until sold out or agreement ends. **No project-level Negotiation/Closing column** — unit sales are deals on unit listings. Unit availability is a grid on the project record (`hold_expires_at`, existing `release_expired_holds` cron).

5. **Broker routine.** Every open opportunity has a dated **next action** (`tasks` with `entity_type = 'seller_opportunity'`). Entering an opportunity stage may insert template tasks (DB trigger + `stageTasks.ts` parity).

## Consequences

- MSA remains buyer-side; seller intake reads MSA, never writes it.
- Qobrix-only stock may keep legacy **Deal workflow** on the record until adopted.
- KB listing-lifecycle doc remains RESO-focused; seller-side ownership is cross-linked here and in the MLS app process doc.
