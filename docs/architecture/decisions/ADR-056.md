# ADR-056: Tenant-bound cross-broker shortlist visibility

**Status**: Accepted  
**Date**: 2026-09-09  
**Scope**: MSA listing details and Matching listing drawer  
**Related**: [security-model.md](../../platform/security-model.md);
[api-contracts.md](../../platform/api-contracts.md);
[compliance.md](../../platform/compliance.md)

## Context

Brokers need to know whether a listing has already been put in front of a client, including
shortlists owned by another broker in the same tenant. Normal RLS on `collections` and
`collection_items` is intentionally scoped to `self` / `team`, so a client-side join cannot
answer that question for every broker.

A service-role Edge Function or a service-harvested cross-broker cache would remove the RLS
guarantee and create a durable client-PII aggregation. The workflow needs only three facts:
the broker display name, the client's first and last name, and the time the listing was added.

## Decision

1. MSA uses a narrow `SECURITY DEFINER` RPC over authoritative `collection_items`,
   `collections`, `opportunities`, and `contacts`. It creates no mirror, cache, or
   materialised view.
2. The RPC derives tenant, user, CRUD permission, and active scope from the signed JWT. Its
   `p_viewer_scope` argument is mandatory and must exactly match `get_active_scope()`.
3. The caller must be able to read the App-DB listing under the `properties_select` privacy
   policy before the RPC may search cross-broker shortlist membership. This prevents guessed
   listing IDs from becoming a client-name enumeration oracle.
4. The result row has exactly four fields:
   `broker_display_name`, `client_first_name`, `client_last_name`, and `date_added`.
   It does not return user IDs, contact IDs, email, phone, notes, budgets, or snapshots.
5. The `listing-shortlist-shares` Edge Function is a thin authenticated proxy using the
   caller's bearer token and anon client. It never uses `service_role`. It allow-lists result
   keys, strips any unexpected fields, and emits `pii_masked_fields` on every request; a
   non-zero value is a contract breach to investigate.
6. The UI helper requires `ViewerScope` at the type level, so omitting viewer context is a
   compile error. Listing and Matching use the same listing drawer implementation.
7. Existing shortlist write rules remain unchanged. Reserved or sold inventory cannot be
   newly attached; this read-only disclosure does not create, copy, or re-share a shortlist.

## Consequences

- A broker can avoid duplicating client outreach without gaining general access to a
  colleague's collection or contact record.
- Client names are deliberately visible tenant-wide for this single coordination purpose;
  all other client fields remain protected by their ordinary RLS paths.
- The App DB must contain a scoped listing identity (local UUID or Qobrix external ID) before
  disclosure can return rows. A not-yet-materialised listing fails closed with an empty set.
- Cross-broker lookup cost is paid at request time against authoritative rows; a partial
  index on listing membership keeps that bounded without changing visibility semantics.

## Alternatives considered

- **Service-harvested cache table** — rejected because it would persist the harvester's
  visibility and duplicate client PII.
- **Client-side joins under collection RLS** — rejected because restricted brokers cannot
  see colleagues' shortlist rows and the feature would under-report.
- **Service-role Edge Function** — rejected because authorization would depend on bespoke
  application filtering instead of the signed caller context and database checks.
- **Return contact or collection identifiers** — rejected under data minimisation; the
  workflow needs human-readable names and the date only.
