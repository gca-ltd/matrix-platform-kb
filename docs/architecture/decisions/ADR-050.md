# ADR-050: Retire the Qobrix service account — MSA as thin client under caller tokens

**Status**: Accepted  
**Date**: 2026-09-01  
**Depends on**: [ADR-044](ADR-044.md) (surface partition + copy-on-write — D1–D2, D3a–D3b, D4–D6 remain), [ADR-046](ADR-046.md) (Qobrix → SSO identity map), [ADR-047](ADR-047.md) (copy ownership + claims)  
**Supersedes**: ADR-044 **D3c** (scope authority: live Qobrix for restricted / mirror for unrestricted) and **D3d** (opportunity + contract mirrors for board reads)  
**Scope**: Matrix Sales Automation (MSA) — `matrix-sales-automation` / staging App DB `ycbwgnihbrqammkgngum`, Qobrix CY CRM bridge

## Context

ADR-044 D3c/D3d institutionalised a **service-harvested** opportunity/contract
mirror (`QOBRIX_SHARE_*`) for unrestricted SSO viewers, with restricted viewers
(`self` / `team`) reading live Qobrix as the caller. That split was the
2026-08-31 remediation after the 2026-08-28 Leads incident (~46k rows / 66
owners with contact PII served from the mirror to Brokers).

The dual-leg merge (mirror ∪ live ∪ App DB) produced repeated merge-gap
regressions, kept a shared upstream credential on the read path, and bound
board performance to Qobrix fan-out for every restricted viewer. Meanwhile
App-DB RLS already encodes the intended split:

- **CRM** (leads, contacts, opportunities) — owner-scoped via
  `can_read_claimed_row` (assignee / creator / claim / team / unrestricted).
- **Listings** (properties, projects) — shared inventory with a private
  carve-out.

With CRM confirmed owner-scoped (no public-opportunity concept), MSA can become
a **thin client**: every Qobrix *fetch* under the caller's own token; every CRM
*screen* reads App DB under MSA RLS; no shared account on any read path.

## Decision

### D1 — Caller-token reads only; MSA is a Qobrix thin client

Every Qobrix HTTP call authenticates with the **browser-held** per-user session
(`x-qobrix-token` / `x-qobrix-cookie`). There is no server-stored per-user
credential and, after cutover, no `QOBRIX_SHARE_*` credential either.

- CRM list/board/detail screens read **App DB only**.
- Qobrix is touched on **explicit refresh**, first materialisation, or the
  documented inventory-search exception (D5) — never on every list open.
- Unattended background harvest is impossible by design; cache staleness is
  bounded by login behaviour and must surface an **"as of"** marker.

### D2 — Owner-scoped CRM; shared listings

| Surface | Visibility after copy |
|---------|----------------------|
| Leads / contacts / opportunities | Owner (assignee) + creator + pending/approved claimant + `team` + unrestricted scopes |
| Properties / projects | Tenant-shared except `private` / `is_private` carve-outs (area-manager / admin helpers) |

No new visibility model is invented — prove existing policies at promoted scale
(~46k opportunities) before cutover.

**Call-centre broadening (recorded).** `leads_select` adds
`OR _is_call_center_or_admin()`, satisfied by a **role-name regex**, not by
SSO scope. A `self`-scope call-centre user therefore reads **every agent's
leads tenant-wide**. That is intentional (inbox triage) but means "restricted
scopes are owner-scoped" is **not** universally true for leads. Visibility
proofs and diff harnesses must classify call-centre (and area-manager) roles
in the unrestricted bucket, or intended tenant-wide access looks like a leak.

Role-name-regex authorisation (`call cent(re|er)`, `area manager|…|admin`) is
fragile (e.g. unanchored `admin` substring). Harden later onto permission keys;
do not silently widen further.

### D3 — Per-user cache refresh (shared storage, owner-scoped RLS)

- **Per-user sync, shared storage.** Rows stay in tenant-scoped
  `opportunities` / `leads` / `contacts` keyed by
  `(tenant_id, external_qobrix_id)` (partial unique where id is present). Do
  **not** build per-user cache tables.
- **Client-driven, chunked.** The browser advances a
  `qobrix_user_sync_state` checkpoint per call so a mid-walk token expiry
  does not lose progress. Cooldown + single-flight + global concurrency cap;
  honour Qobrix `429` / `retry-after`.
- **Ownership from the Qobrix payload**, resolved through
  `qobrix_user_sso_map` — never from the refresher's session.
- **Delete signal** = Qobrix `trashed` field. Do not prune "untouched by my
  pass" (that deletes other agents' rows under per-user visibility).
- Assignment divergences raise the existing claim machinery
  (`x_mirror_owner_mismatch` / `mirror_claim_state`, …); admin adjudicates
  ownership.

### D4 — `created_by` is the resolved owner, never the refresher

All CRM/listing cache writes go through a `SECURITY DEFINER` admission RPC.
`created_by` is set to the **resolved owner** (or a system sentinel when none
resolves). Stamping the caller as creator converts a point-in-time upstream
grant into a durable MSA grant via the creator branch of
`can_read_scoped_row` — the 2026-08-28 leak shape with a person as harvester.
Direct client INSERTs on those tables are forbidden.

### D5 — Inventory search stays live caller-token (documented exception)

Catalog **search** remains a live Qobrix read under the caller's token (no bulk
promotion of the full catalog). Listings already copied stay App-DB; first open
still materialises. Search is the one surface that may fail hard during a
Qobrix outage; CRM boards degrade to bounded staleness instead.

### D6 — Mirrors removed before Qobrix sunset

Drop `qobrix_opportunity_mirror`, `qobrix_contract_mirror`, sync crons,
`share-service-session` harvest paths, and the mirror query/guardrail module
**before** the ecosystem Phase 7 Qobrix decommission (~Feb 2027). The
per-user cache replaces the mirror's only remaining purpose (performance for
broad readers) without a shared credential or dual-leg merge.

## Deliberate divergences

### From ADR-044 D3c/D3d (timeline)

ADR-044 kept scope-gated mirrors until Qobrix sunset. This ADR removes them
earlier. Justification: merge drift on every dual-leg surface; rate-limit
exposure proportional to page views; service credential on the read path. The
KB is updated in the same change (this ADR + security/performance/ecosystem
docs), not as a one-off exception.

### From the 2026-08-31 remediation (read authority)

That remediation restored **Qobrix as ACL authority** for restricted viewers
because MSA-side owner filters under-showed relative to Qobrix's richer ACL.
This ADR makes **MSA RLS authoritative for CRM reads**.

Justified **only** because CRM rows are owner-scoped with no shared-visibility
concept, so owner equality reproduces Qobrix visibility for ordinary brokers —
and a per-broker row-set diff against live Qobrix must prove it before live
promotion. If any sampled restricted broker loses rows, this divergence is not
authorised and cutover stops. Call-centre / area-manager broadenings are
explicit MSA exceptions (D2), not Qobrix ACL reconstructions.

## Consequences

- **Post-promotion RLS performance (2026-09-01 hotfix).** Phase 4 promotion
  (~43k leads, ~46k contacts) turned a latent planner issue into a hard
  availability bug: `(SELECT can_read_claimed_row(row…))` on a
  `SECURITY DEFINER` helper became a per-row `SubPlan` (`loops=43359`,
  **10,028 ms** vs **8 s** `authenticated` `statement_timeout`). CRM list
  counts and `qobrix-crm-mirror` returned 500. Fix: inline the predicate into
  `leads` / `contacts` / `opportunities` policies (InitPlan for caller
  identity, bare columns for row terms) — **2.4 ms** for the same query.
  See [`performance.md`](../../platform/performance.md) § MSA / Qobrix read path.
- Delete `QOBRIX_SHARE_*` after last legitimate use (bulk promotion / image
  rewrite); rotate credentials.
- Pipeline **and** Leads read App DB; shared admission module + contract test
  replace dual-leg merge.
- Org-wide aggregates use App DB with the same "as of" freshness.
- Users without a Qobrix account cannot refresh; they are read-only over rows
  colleagues have warmed.
- ADR-044 D1–D2, D3a–D3b, D4–D6 (stage map, contract column overrides,
  copy-on-write SoT, nurture, dedup) remain in force.
