# ADR-032: Chat-identity binding + delegated minting for the ITSM MCP (chat agent)

**Status**: Obsolete  
**Date**: 2026-06-16  
**Superseded as platform MCP reference by**: [ADR-039](ADR-039.md) (Qobrix stack). ITSM MCP edge functions may still exist in `matrix-itsm` but are no longer the normative Matrix MCP pattern.  
**Extends**: [ADR-011](ADR-011.md) (ES256 SSO signing), [ADR-012](ADR-012.md) (SSO as the sole identity authority; identity boundary), [ADR-019](ADR-019.md) (server-managed PKCE / bounded replay), [ADR-027](ADR-027.md) (Third-Party Auth for own-DB apps)
**Scope**: SSO project `xgubaguglsnokjyudgvc` (new `sso_delegation_grants` table, `mcp_resolve_user` RPC, `mint-delegated-token` EF) + ITSM app `matrix-itsm` (app DB `irjrcskfcyierdbefrpk`: `mcp_chat_links` / `mcp_link_requests` / `mcp_action_consents` / `mcp_oauth_grants`; `mcp_oauth_clients` carries `client_secret_hash` / `redirect_uris` / `is_agent`; `mcp-server` / `mcp-oauth` / `mcp-admin` EFs; `/oauth/consent` + `/mcp/link` pages).

> **2026-08-21:** Platform MCP reference moved to ADR-039 (qobrix-crm-mcp + qobrix-crm-mcp-oauth). Do not use this ADR for greenfield MCP servers or clients.

> **2026-08-17 (ADR-038):** MCP access tokens are now signed **ES256 (P-256)**; the HMAC tier described below is retired. Regenerate the key from Settings → MCP after deploy.

> **2026-06-17b revision (supersedes the 2026-06-17 `private_key_jwt` revision).** Agent auth is now **HubSpot-style OAuth 2.1 authorization-code + PKCE + refresh**, so any MCP client (Claude, Cursor, or a custom agent) can connect with the familiar **Client ID + Client Secret + browser Authorize**. Every agent authenticates the **same way**; each agent is its own OAuth client. Agent clients are **confidential** (`client_id` + `client_secret`, hashed at rest); interactive personal clients stay **public** (PKCE only, dynamic registration). The earlier `private_key_jwt` / client-credentials path and the `mcp_client_assertions` table are **removed** — they could not be configured in mainstream agent connector UIs. The signing key (`app_settings.mcp.jwt_secret`) stays **server-only**: it signs issued MCP access tokens and is never a bearer. Per-user authority for private tools is unchanged (delegated minting / OBO via `X-Chat-*` headers, below).

## Context

The new requirement: the **chat agent** (an LLM over Telegram / WhatsApp /
Microsoft Teams) must call the MCP as a tool **on behalf of chat users**, while
holding **no SSO tokens and no per-user credentials**. The agent knows only the
chat platform and the platform's permanent user id. We must:

1. Bind a messenger account to a Matrix (SSO) identity **once**.
2. Thereafter let the agent act for that user **without** it ever holding a
   credential, with Postgres **RLS** enforcing access as the real user.
3. Keep SSO the **sole identity authority** (ADR-012) — no duplicated identity
   custody, no stored refresh tokens.

A rejected earlier design stored encrypted SSO refresh tokens in the ITSM DB.
That duplicates identity custody and creates a high-value token vault — exactly
what ADR-012 forbids.

## Decision

### 1. Delegated minting (no stored user credentials)

The SSO project gains a **`mint-delegated-token`** edge function. On each MCP
request for a linked chat user, the MCP asks SSO to mint a **short-lived
(~30 min) ES256 JWT** for that user against a **revocable delegation grant**.
The MCP caches the token **in memory for its lifetime only** and runs tools
through a **per-user RLS-bound PostgREST client** (Supabase Third-Party Auth,
ADR-027). No token is persisted anywhere; access ends when the grant is revoked
or expires.

The minted JWT carries the user's **real** scope/crud/tenant claims (same shape
`oauth-token` / `switch-role` emit) so RLS returns correct data. Least privilege
is enforced at two **other** layers: the agent is limited to a reduced **tool
surface** (tickets r/w, assets read, KB read, profile, tool_guidance), and sensitive/write
actions require **step-up consent** (below).

`sso_delegation_grants` columns: `user_id`, `client_id` (the ITSM-MCP delegate),
`platform`, `external_user_ref` (chat id, audit/dedup), `assurance`, `status`,
`created_at`, `revoked_at`, `last_minted_at`, `mint_count`. Service-role only.

### 2. Agent authentication = OAuth 2.1 authorization-code + PKCE (HubSpot-style)

Every agent authenticates the **same way** — the method is shared, the credential
is per-agent:

- **Each agent is its own OAuth client** (`mcp_oauth_clients` row, `is_agent=true`)
  with its own **`client_id` + `client_secret`** and registered **`redirect_uris`**.
  The secret is stored two ways: a **SHA-256 hash** (`client_secret_hash`, used by
  `mcp-oauth` for token-endpoint verification) **and** an **AES-256-GCM ciphertext**
  (`client_secret_enc`) so an admin can **re-Show** it from Settings → MCP → Agents →
  Manage (HubSpot parity). The encryption key (`MCP_SECRET_ENC_KEY`, 32 bytes) lives
  **only** in the `mcp-admin` function env — `mcp-oauth` never needs it. Reveal is
  **admin-only and audited** (`mcp_audit_log`, `tool='reveal_secret'`). Deleting an
  agent is **permanent** (`delete_agent` removes its tokens + client row). The agent
  runs the standard browser flow:
  `mcp-oauth/authorize` → `/oauth/consent` (the operator signs in **once** via SSO
  and approves) → single-use authorization `code` → `mcp-oauth/token`
  (`grant_type=authorization_code`, PKCE `code_verifier`, **plus `client_secret`**
  for confidential agent clients) → a **1h MCP access token + 30d refresh token**.
  The issued token is flagged `is_agent`. Refresh rotates the refresh token.
  Revocation and audit attribution are **per-agent**.
- **Interactive personal clients stay public** (Claude/Cursor): PKCE only
  (`token_endpoint_auth_method = none`), via dynamic client registration
  (`/register`). Their tokens are normal user tokens and act as the signed-in user.
- **Signing key is server-only.** `app_settings.mcp.jwt_secret` signs/verifies the
  issued MCP access tokens and is **never** a bearer or shared with agents.
  (Managed from Settings → MCP → Configuration; masked in the UI.)
- **End-user identity is asserted via request headers** (`X-Chat-Platform`,
  `X-Chat-Scope`, `X-Chat-User-Id`, `X-Chat-Aad-Oid` for Teams), never via
  LLM-controllable tool arguments. The headers select the end user; the OAuth
  access token authenticates the agent.
- **MCP → SSO service credential** (`MCP → mint-delegated-token`): an SSO-side
  shared secret (`MCP_DELEGATION_SECRET`) in the ITSM EF environment, checked by
  the mint EF via the `X-Delegation-Secret` header.

This is a three-plane separation: inbound agent auth (OAuth authorization-code +
PKCE + client_secret), access control (public/private tiering + per-request
validation + revocation), and outbound per-user auth (delegated mint). The
credential reaching the agent is never the credential reaching the data.

### 2a. Public vs private tool tiering

Tools split by whether they need a verified 1:1 identity:

- **Public** (`whoami`, `tool_guidance`, `search_kb`, `get_article`, `create_ticket`): require
  **only** a valid agent access token (bearer). No per-user identity, no linkage,
  and they **never** trigger the SSO link/confirmation URL. They run under the service
  role with leak-safe queries (KB published-only; `create_ticket` is write-only
  and attributes the requester from args or a generic sentinel when unverified).
  Descriptions use a HubSpot-style structure (`<capabilities>` / `<when_to_use>` /
  `<returns>` / `<usage_guidance>`) so LLMs can chain tools effectively.
- **Private** (`list_tickets`, `get_ticket`, `update_ticket`, `search_assets`, `get_asset`):
  require a verified **1:1** identity and a linked SSO account; they run under
  the minted per-user token + RLS.
- **Link** (`link_account`): one-time SSO binding for Telegram/WhatsApp before private tools.

**Identified** = `X-Chat-Scope` != `group` **AND** either a usable chat user id on a
known platform (`telegram` | `whatsapp` | `teams`) **or** (for `web`) a present
`X-Chat-User-Bearer` SSO access token verified on every request. A **group** chat
(or a direct chat with **no** identity proof) can only **execute** public tools, but `tools/list` still returns the **full catalogue**
with `tier` annotations (`public` | `private` | `link`) and `<availability>` notes
in each description so the LLM knows what exists. When a private tool is called
without identity, the MCP returns a JSON-RPC `private_requires_dm` error (`-32003`)
whose `data` carries `cause` (`group_chat` | `no_user_id` | `no_verified_session`
for web), `tier`, `chat_scope`,
`platform`, `remediation: ask_user_to_dm`, `agent_guidance`, and `available_here`
(the public tools still usable). The agent relays this in its own words, nudging
the user to re-send the request in a direct (1:1) message — no sensitive data is
leaked. The link/SSO-confirmation URL appears only in a 1:1 context once a private
tool needs linkage (`not_linked`).

### 3. Per-platform binding & assurance

- **Teams** → **auto-bind**, **high** assurance. `aadObjectId` = SSO `azure_oid`;
  the mint EF resolves the user via `mcp_resolve_user(azure_oid|email)` and
  creates the grant on first call. No interactive login.
- **Telegram / WhatsApp** → **one-time interactive SSO login** at `/mcp/link`,
  **interactive** assurance. The `link_account` tool returns a single-use URL;
  the user signs in (transparent if a session exists), and `mcp-oauth/link_complete`
  records the mapping + grant. Anchor on the **numeric/permanent** platform id
  (never `@handle`/phone).
- **Web (in-app chat)** → **auto-bind**, **interactive** assurance. The
  webchat forwards the logged-in user's own SSO access token in
  `X-Chat-User-Bearer`; `mcp-server` passes it to `create_grant(user_bearer)` on
  every request (same verification path as Telegram/WhatsApp `link_complete`, but
  inline — no `/mcp/link` page). `X-Chat-User-Id` must equal the bearer `sub`
  (SSO user UUID). `link_account` is not used for web.

### 4. Step-up consent

On linked agent sessions, ticket **close/resolve** via `update_ticket` requires a
fresh **click-through** confirmation (defense-in-depth on any channel).
The tool returns `consent_required` + a `/mcp/link?step=…` URL; the user confirms
(SSO-authenticated, same identity), and the action is authorized for ~5 min,
single-use, keyed by chat identity + action + target. No token is handed back to
the agent.

### 5. Trust chain (must be authenticated end-to-end)

`Platform → (signed webhook) → chat agent → (OAuth code+PKCE+secret → MCP access token) →
MCP → (service cred) → SSO mint`. The chat id is **platform-asserted**, never user-asserted; the agent
**must** verify the platform webhook signature (Telegram `X-Telegram-Bot-Api-Secret-Token`,
WhatsApp `X-Hub-Signature-256`, Teams Bot Framework JWT) before forwarding a chat
id. For **web**, the proof is the user's own SSO bearer (`X-Chat-User-Bearer`) verified
cryptographically on every request — not a bare `X-Chat-Verified` flag. See `sso-edge-functions.md` and `api-contracts.md`.

## Consequences

- SSO remains the sole identity authority; **no user credentials** are stored in
  ITSM (only mappings + flow state). Grants are revocable per-user from
  Settings → MCP (revoke also revokes the SSO grant) and auto-expire after **90
  days of inactivity**.
- Blast radius of a leaked **agent client secret** is bounded and **per-agent**:
  rotate the secret (new hash + ciphertext, old tokens revoked) or permanently
  **delete** that one agent (drops its tokens + client row) without touching the
  signing key or any other agent. The secret is stored AES-256-GCM-encrypted so it
  can be re-shown, but the key is `mcp-admin`-only and every reveal is audited, so a
  DB-only read does not yield plaintext secrets. A leaked
  **signing key** can not be replayed as an agent credential (it is server-only and
  not a bearer). Private-tool exposure is further bounded by reduced tool surface,
  per-request short-lived per-user tokens, RLS, step-up consent, and audit. A
  leaked chat id alone grants nothing (the agent OAuth credential + webhook
  verification are the linchpins).
- Residual risks: account compromise (SIM-swap/stolen session), WhatsApp number
  recycling, and the assurance downgrade of personal TG/WA vs corporate Teams.
  Mitigated by one-time strong binding, inactivity expiry, step-up for writes,
  `last_seen` visibility, and treating TG/WA as lower assurance.
- GDPR/consent: linking a messenger id to an employee identity is a deliberate,
  user-initiated, revocable act with clear consent copy on `/mcp/link`; the
  binding is the only personal datum stored and is admin-visible/erasable.

## Provisioning (one-time)

- Provision `MCP_DELEGATION_SECRET` on both the SSO `mint-delegated-token` EF and
  the ITSM EFs (`mcp-server`, `mcp-oauth`, `mcp-admin`).
- Provision `MCP_SECRET_ENC_KEY` (32 bytes, hex or base64) on the `mcp-admin` EF
  only — it encrypts/decrypts the agent `client_secret_enc` for the admin Show
  action. Do **not** set it on `mcp-oauth`/`mcp-server`.
- Register `/mcp/link` and `/oauth/consent` as redirect URIs on ITSM's SSO client.
- Ensure the MCP signing key is generated in Settings → MCP → Configuration
  (`app_settings.mcp.jwt_secret`) — server-only, never handed to an agent.
- Register each agent in Settings → MCP → Agents (enter a name + the agent
  platform's redirect URL). Copy the generated `client_id` + `client_secret` and the
  MCP URL into the agent connector, then click Authorize to complete the OAuth
  handshake. The secret can be re-shown or rotated any time from **Manage**, and more
  redirect URLs added there without recreating the agent.
