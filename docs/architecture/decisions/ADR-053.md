# ADR-053: In-app build-status surface — repo Markdown, structure-agnostic renderer, `alwaysVisible` nav

**Status**: Accepted  
**Date**: 2026-09-03  
**Scope**: Matrix Sales Automation (pattern reusable by other Matrix apps)  
**Related**: [app-template.md](../../platform/app-template.md) (routing / sidebar / `ProtectedRoute`);
[ADR-021](ADR-021.md) (runtime i18n); [ADR-036](ADR-036.md) (MSA app-local i18n corpus);
[ADR-045](ADR-045.md) (`ProtectedRoute` loading vs denial)

## Context

Product coordination for MSA lived in a maintained Markdown file
(`MSA-build-status-YYYY-MM-DD.md`): backlog tables, delivered items, effort
estimates, and an appendix of user conversations. Brokers and managers had no
in-app place to open that file. They needed:

1. A sidebar entry at the bottom, **visible to every signed-in user**.
2. A Markdown viewer with table of contents, keyword search, and deep links.
3. A path to **raise** something specific against a section, via the existing
   in-app chat widget.

The document is expected to change shape over time (new sections, different
heading depths, renamed tables). Hard-coding section names or derived KPI
tiles would break on the next rewrite.

Platform convention ([app-template.md](../../platform/app-template.md)) is that
every route uses `ProtectedRoute` with `requiredPage`, and the sidebar filters
on `canAccessPage(pageKey)`. New page keys appear in Administration → Roles
**unchecked by default**, so "available to all" is not achievable by adding a
nav item alone.

## Decision

### D1 — Repo-sourced Markdown under `docs/build-status/`

Snapshots live in the app repo as `YYYY-MM-DD-<slug>.md`. The SPA discovers
them with lazy `import.meta.glob('…/*.md', { query: '?raw' })`. Updating the
status is: edit / add a file → commit → push → watcher deploy. No App DB
table and no in-app editor in this iteration.

### D2 — Structure-agnostic parser and renderer

- Front matter: pandoc `%` lines, YAML `---`, or none.
- TOC from all ATX headings `#`…`######`, nested by actual level; headings
  inside fenced code blocks are ignored.
- GitHub-style slugs with numeric de-duplication.
- `react-markdown` + `remark-gfm` with an explicit component map for all
  common block types (no assumption about which sections exist).
- Keyword search via the existing `tokensMatchHaystack` helper over per-section
  plain-text indexes.
- No derived KPI chips from the Markdown — the document author writes the
  summary; the UI displays it.

### D3 — `alwaysVisible` nav items + auth-only route

Extend the nav registry with `alwaysVisible?: boolean`:

- Sidebar / mobile nav: `item.alwaysVisible || canAccessPage(item.pageKey)`.
- `PAGE_PERMISSION_GROUPS` (Roles editor) **excludes** `alwaysVisible` items
  and drops empty groups, so an admin cannot un-grant a page the code always
  shows.
- Route: `<ProtectedRoute>` **without** `requiredPage` (same pattern as
  `/menu`) — authentication only.

This is a deliberate, documented divergence from the default
"every route has `requiredPage`" rule. Prefer a new `pageKey` plus
`alwaysVisible` over reusing `home` / `profile` (those still need grants for
non-admin roles).

### D4 — Raise this → existing AI chat (prefill only)

"Raise this" on a heading opens the floating Ask AI chat
(`AiDataChatWidget`) via a window `CustomEvent`, with the input prefilled
with the section title, snapshot label, and deep link. The message is **not**
auto-sent. This does **not** create a backlog row — tracking intake is a
future decision if needed.

## Consequences

- Positive: one central in-app coordination surface; document evolution needs
  no code change; every signed-in user sees it without role edits.
- Positive: `alwaysVisible` is an explicit, testable contract rather than
  "hope every role has `home`".
- Negative / follow-up: content updates require a deploy (acceptable for
  day-batch coordination). A later DB-backed editor can reuse the same parser.
- Negative / follow-up: Raise this does not persist a request; operators still
  triage via chat / Teams / the Markdown appendix.
- Apps adopting the pattern should cite this ADR and keep chrome strings in
  `en.json` + `app_ui_strings` with an `APP_I18N_VERSION` bump.
