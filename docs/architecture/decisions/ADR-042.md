# ADR-042: Per-client_id SSO localStorage namespacing

**Status**: Accepted  
**Date**: 2026-08-25  
**Depends on**: [ADR-011](ADR-011.md) (ES256 SSO JWTs), [ADR-018](ADR-018.md) / [ADR-027](ADR-027.md) (Third-Party Auth)  
**Scope**: All Matrix SPAs co-hosted on `intranet.sharpsir.group` (shared browser origin)

## Context

Every Matrix SPA under `https://intranet.sharpsir.group/<subpath>/` shares one
browser origin and therefore one `localStorage`. Historically each app wrote its
SSO session to the same keys (`matrix_sso_access_token`, refresh/user/PKCE keys)
and opened the same `BroadcastChannel('matrix_sso_tokens')`.

Opening a second app (e.g. Portal minting an HS256 token) overwrote the first
app's ES256 token. The first app's App DB PostgREST calls then failed with
`PGRST301` ("No suitable key or wrong key type"), surfaced in MSA as "Qobrix
temporarily unavailable" (ticket SR000512).

A client-side audience check alone is insufficient while apps still *write* the
shared key; the write path must be partitioned.

## Decision

### D1 — Namespace storage keys by OAuth `client_id`

Each app stores SSO session material under:

```
matrix_sso_access_token.<sanitized_client_id>
matrix_sso_refresh_token.<sanitized_client_id>
matrix_sso_user.<sanitized_client_id>
… (same for PKCE, role-switch, supabase legacy token keys)
BroadcastChannel: matrix_sso_tokens.<sanitized_client_id>
```

`client_id` comes from `getClientId()` / `VITE_SSO_CLIENT_ID`, or the hardcoded
`CLIENT_ID` in older apps. Fallback: Vite `BASE_URL` path segment.

**Why client_id, not base path:** `/agency-portal` and the Portal SPA share one
OAuth client (`sharp-matrix-vm-sso-v2-…`) and must share one session. Keying on
path would incorrectly split them.

### D2 — Audience guard on read

`MatrixSSOStorage.getAccessToken()` rejects (and clears) a stored token whose
JWT `client_id` claim is not this app's. All SSO mint paths (`oauth-token`
authorization-code + refresh, `switch-role`, `switch-tenant`,
`mint-delegated-token`) stamp `client_id` into the payload.

### D3 — One-time legacy adoption

If the namespaced key is empty but the legacy shared key holds a token minted
for *this* `client_id`, copy it into the namespaced keys and remove the legacy
session keys. Foreign-app legacy tokens are left untouched. Adoption must **not**
delete another app's in-flight PKCE `code_verifier` / `oauth_state`.

### D4 — Callers go through `MatrixSSOStorage`

Raw `localStorage.getItem('matrix_sso_*')` outside `matrix-sso.ts` is forbidden;
use `MatrixSSOStorage` helpers (`getUser`, `clearCodeVerifier`, etc.).

## Consequences

- New remixes from `matrix-apps-template-2-1` / `2-2` are born correct.
- Existing apps re-login once if they were silently riding a foreign token;
  worst case is one extra sign-in per app.
- Convergence is monotone: no coordinated cutover. Fixed apps stop writing the
  contested key; unfixed apps keep clobbering each other until rolled out.
- Server-side `aud` / `client_id` enforcement on App DB remains a separate
  hardening item; this ADR only partitions the browser storage plane.
