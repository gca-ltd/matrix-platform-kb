# ADR-059: Matrix MCP Profile — standard auth only

**Status:** Accepted
**Date:** 2026-09-29

## Context

Matrix runs several MCP servers (Qobrix, MSA, Charts, HU, Datacore) and one general client (Digital Employees). Auth was described as "Modes A–D", `server_managed`, and "URL-mode authorization", and two servers accepted custom `X-Chat-*` or `X-Api-*` headers. Those names do not match MCP 2025-11-25 or the auth types Digital Employees shows to administrators (None, API key, User OAuth 2.1, Service OAuth 2.1). A client or server built from the old docs could not interoperate with Claude, Cursor, or Dust without a Matrix-specific path.

## Decision

1. The normative contract is [docs/platform/mcp/](../../platform/mcp/README.md). Protocol `2025-11-25`, fallback `2025-06-18`.
2. The only auth types are `none`, `api_key` (RFC 6750 Bearer), `oauth_user` (authorization code + PKCE), and `oauth_service` (client credentials).
3. Custom auth headers are retired. `X-Chat-*` and `X-Api-User` / `X-Api-Key` are not part of the profile. Qobrix keeps them behind an explicit legacy flag only until the sunset in the server changelog.
4. The retired names exist in one table, [glossary.md](../../platform/mcp/glossary.md#retired-terms). They are banned everywhere else. `tools/mcp-conformance/check-mcp-terminology.mjs` enforces that.

This supersedes:

- ADR-039's mode taxonomy (the RS/AS split and the no-token-passthrough rule still stand).
- ADR-040 D1's `server_managed` mode.
- ADR-041's signed-header row.
- ADR-058's URL-mode / `X-Chat-*` path. MSA is `oauth_user` with `identityProbe` on `msa_whoami`.

## Consequences

- Digital Employees registers MSA as `oauth_user` with `identityProbe: { tool: "msa_whoami", emailPath: "email" }`.
- Qobrix HTTP accepts `api_key` and `oauth_user`. The authorization server shows the client name and redirect host before login.
- New servers copy the profile. They do not invent a fifth auth type.
