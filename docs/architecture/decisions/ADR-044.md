# ADR-044: Qobrix Opportunity surface partition (Leads vs Pipeline)

**Status**: Accepted  
**Date**: 2026-08-27  
**Depends on**: [ADR-029](ADR-029.md) (contract status → Pending/Closed), [ADR-036](ADR-036.md) (Qobrix-vanilla-inside App DB)  
**Scope**: Matrix Sales Automation (MSA) — `matrix-sales-automation` / staging, Qobrix CRM mirror

## Context

Qobrix exposes a single `Opportunity` resource (UI label “Lead”) whose free-text
`status` is a tenant workflow stage. Contracts live in a separate `Contract`
resource keyed by `opportunity_id`. MSA separates that journey into two surfaces:

1. **Leads** — pre-qualification inbox (call centre / broker assignment).
2. **Pipeline** — sales board from qualification through payment, with Won/Lost
   terminal columns and contracts as board position signals.

Before this ADR the board fetched only `status=="in_process"` (a call-centre
stage in the live tenant) and collapsed sales stages into a catch-all, so the
wrong records appeared on the pipeline while real deals were hidden. Leads and
Pipeline also overlapped on the same Qobrix rows.

Two different meanings of “qualification” must stay distinct:

| Term | Meaning |
|------|---------|
| **Lead qualification** | `leads.status` → `qualified` via `qualify_lead_v2` (hand off to broker / pipeline). |
| **Pipeline `qualification` column** | First board column; gate to Matching checks requirements completeness. |

## Decision

### D1 — Workflow stage decides the surface

Per-tenant map (`qobrix_stage_mappings` + default resolver in
`qobrix-stage-map.ts` / `qobrixStageMap.ts`):

| Qobrix stage (wire) | Surface | MSA state / column |
|---------------------|---------|--------------------|
| `new` | Leads | `new` |
| `in_process` / `open` | Leads | `contacting` |
| `enquiry` | Leads | `enquiry` |
| `potential` | Pipeline | `qualification` |
| `appointment` / `appt_follow_up` | Pipeline | `viewing` |
| `closed_won` / `won` | Pipeline | `won` (read-only) |
| `closed_lost` / `lost` | Pipeline | `lost` (read-only) |
| `asleep` | Leads | `nurturing` |
| `not_interested` | Leads | `disqualified` |
| Unknown | Leads | counted as `hidden.unmapped_stage`, not silently dropped |

Leads default filter is **Open** (`new|contacting|enquiry|nurturing`), not All,
so converted `qualified` twins do not sit beside their pipeline card.

### D2 — Contract overrides pipeline column (not surface)

Buyer contracts only (`cos`, `tenancy_agreement`); mandates never advance the board:

| Signal | Column |
|--------|--------|
| `title_deed_status = transferred_to_buyer` | `won` |
| `contract_status = reserved` | `contracting` |
| `contract_status = agreed` / `signed` / `completed` / `closed` | `payment` (Pending edge per ADR-029) |
| `cancelled` + no `date_of_contract` | non-event |
| `cancelled` + dated, not materialized | re-enter `matching` |
| `cancelled` + materialized | no auto-move (mismatch workflow) |

Qobrix has no opportunity-level `contracting` / `payment` status. Those MSA
columns are fed exclusively by buyer-contract signals. Live OR-batch fetches
against `/contracts` were removed from the board read path (timeout); contract
hints come from `qobrix_contract_mirror` (see D3d) with MSA-authored
`public.contracts` winning on the same opportunity (copy-on-write).

### D3 — Column precedence

1. Lifecycle / demoted (`x_demoted_to_lead_id`, non-active lifecycle) → off board  
2. **Lost** Qobrix status (`closed_lost` / `lost`) → Lost column (outranks local stage and contracts)  
3. Local `x_current_stage` (MSA is SoT once materialized)  
4. Title deed / contract (D2) — outranks Qobrix `closed_won`  
5. **Won** Qobrix status (`closed_won` / `won`) → Won column  
6. Stage map (D1)  
7. Matching-readiness heuristic → `matching` else `qualification`

MSA Won means payment complete (title transferred or explicit won). Qobrix
`closed_won` is deal agreement — a different event — so an in-flight buyer
contract places the deal in Contracting/Payment even when Qobrix already
closed the opportunity. The open board therefore admits `closed_won` rows that
carry an in-flight buyer contract (reserved / agreed / signed without title
transfer) without requiring “Show closed”.

### D3a — Opt-in terminal columns

Won/Lost columns are **not** fetched on every board load. The kanban “Show closed”
toggle passes `include_closed` to `qobrix-pipeline`; only then does the EF run the
terminal status wave (optionally date-bounded via `from`/`to`). Default board stays
five progression columns.

### D3b — Stage map table vs code constant

`public.qobrix_stage_mappings` is the per-tenant override source of truth for the
board EF (loaded once per invocation). Empty / missing rows fall back to
`DEFAULT_STAGE_MAPPINGS` in `qobrix-stage-map.ts`. The frontend mirror
(`qobrixStageMap.ts`) stays on the code constant — it only backs the App-DB
fallback path when Qobrix is unavailable.

### D3c — Scope authority (Qobrix for restricted; mirror for unrestricted)

**Qobrix owns its permission model.** Restricted SSO scopes (`self` / `team`)
must read live Qobrix as the caller (`serveQobrix` / `qFetch` with the user's
`x-qobrix-token`). MSA must **not** invent an `owner==CURRENT_USER` pushdown
that would hide rows Qobrix would grant (team / office / delegation). This
matches commit `98dc263b` (2026-08-19) for Leads and extends to Pipeline board
reads for restricted viewers (2026-08-31).

Unrestricted scopes (`global` / `org_admin` / `system_admin`) may use the
tenant-global mirror and remain unscoped on live fallback.

**App-DB local-only** rows still filter via `x_assigned_user_id` /
`owner_team_id` (MSA SoT after materialize). Shared helpers live in
`_shared/qobrix-viewer.ts` (`resolveViewer`, `maskUnownedContactPii`).

**Defence-in-depth:** restricted list/board responses strip contact
name/phone/email from rows whose Qobrix owner is not one of the viewer's
Qobrix identities. Rows and owner labels stay visible for the claim/request
flow. A non-zero `pii_masked_rows` / `leads_pii_mask` / `pipeline_pii_mask`
counter means Qobrix may not be filtering per user — escalate immediately.

A named `BOARD_MAX_ROWS` ceiling (default 2000, env-overridable) remains only as a
safety valve. The response reports `total` (upstream board-eligible count),
`truncated`, and `pagination.has_next_page` so the UI can show “showing X of N”
instead of a false total.

**Sortability follows the read path, and must be a whitelist.** Because D3c
routes restricted viewers onto live Qobrix, the set of sortable columns now
varies by viewer scope. Two consequences:

1. Qobrix rejects an unknown sort field outright — `Invalid sorting expression:
   Variable "x" is not valid` — rather than falling back. Forwarding an
   unmapped client key therefore 500s the whole list rather than ordering it
   wrong, so the mapping is a verified whitelist
   (`QOBRIX_LEAD_SORT_FIELDS` in `qobrix-crm-mirror/index.ts`): `created`,
   `source`, `enquiry_type`, `list_selling_price_to`, `status`. Contact sorts
   only by UUID foreign key (association-path sort such as
   `ContactNameContacts.last_name` is refused), `location` does not exist on
   Opportunity, and owner would order by opaque id rather than broker name.
2. A column affordance must be **derived from the response**, never hardcoded.
   The list response carries `source` (`mirror` / `qobrix`) and
   `applied_sort` (`null` when the server could not honour the request) so the
   client can withhold the arrow instead of showing a highlighted header over
   unchanged `-created` order. Mirror-path sort keys with no case in
   `mirrorSortColumn` (e.g. `campaign`) are no-ops on every path and must not
   offer an arrow at all.

### D3d — Opportunity and contract mirrors for board reads

Board-eligible Qobrix opportunities are mirrored into
`public.qobrix_opportunity_mirror` (separate from MSA-authored
`public.opportunities`) by `qobrix-opportunities-sync` on a 5-minute cron,
advancing `qobrix_sync_cursors.opportunities_cursor` on the sentinel tenant
`00000000-0000-0000-0000-000000000000`. The mirror is **tenant-global** —
keyed solely on `external_qobrix_id` — because Qobrix is a single account
behind one API credential (same convention as `qobrix_user_cache`).

**Mirror reads are only valid for unrestricted SSO viewers.** The table has
RLS enabled with **no policies** (service-role only) and no `tenant_id`. It
was harvested under `QOBRIX_SHARE_*` and therefore carries that account's
visibility. Serving it to a Broker (`self`) silently launders the service
account's book — measured 2026-08-31: ~46k rows / 66 owners with contact PII
on the Leads list. Call sites must pass `viewerScope: { unrestricted: true }`
into `queryOpportunityMirror` / `queryMirrorOnly`; the functions throw for
restricted callers. Guardrail: `scripts/check_mirror_viewer_scope.mjs`.

Buyer contracts (`cos` / `tenancy_agreement`) are mirrored the same way into
`public.qobrix_contract_mirror` by `qobrix-contracts-sync` (5-minute cron,
offset +2 min), advancing `contracts_cursor` on the same sentinel. Board reads
select typed contract columns only; `raw_qobrix` is retained so
`backfill-opportunity-from-qobrix` can copy contracts into tenant-scoped
`public.contracts` when an opportunity is materialized (D4).

For **unrestricted** viewers the board EF prefers the opportunity mirror when
newest `synced_at` is within 30 minutes and falls back to live Qobrix
otherwise. **Restricted** viewers always read live Qobrix as the caller.
Board reads select **typed columns only** (`status`, contact fields, budget,
owner, `source`, `campaign_id`, …); `raw_qobrix` is retained for debugging /
re-sync but is never selected on the read path. Full sync prunes rows whose
`synced_at` predates the run (only when every page and upsert succeeded).
Board SQL shape:

```text
qobrix_opportunity_mirror
  LEFT JOIN opportunities ON external_qobrix_id
  + qobrix_contract_mirror keyed by opportunity_qobrix_id
```

Local-only deals (`external_qobrix_id IS NULL`) remain a separate union from
`opportunities`. Column precedence (D3) still applies after the join — local
stage / contract hints / lost status outrank the mirrored status.
Never write untouched Qobrix rows into `opportunities` solely to speed the board
(that would erase D4’s copy-on-write boundary).

Contract-admitted `closed_won` / `won` rows (in-flight buyer contract, no
title transfer) **obey the board creation-date range** the same way every
other column does. Out-of-range matches are counted into `open_out_of_range`
so the UI disclosure banner still surfaces them. The live-Qobrix fallback
does **not** OR-batch those ids (performance.md); a stale mirror therefore
skips Contracting/Payment for `closed_won` until the next sync.

Qobrix currently carries almost no `title_deed_status = transferred_to_buyer`
signal, so the contract rung alone never releases a deal to MSA Won — agents
(or a future title-transfer sync) must advance the local stage. On
materialize, `backfill-opportunity-from-qobrix` sets `x_current_stage` from
the mirror contract column when present so the first open does not pin a
Payment card to Won.

A board must never issue a second full-collection fetch to resolve a single
record (use `opportunity_board_row` / `getBoardOpportunityByQobrixId`).
Date filters use the generated `qobrix_created_date` column
(`Asia/Nicosia`) so creation-day windows match the CY office calendar.

### D4 — Copy-on-write remains authoritative after mirror

Materialize on open; stamp `mirror_complete_at`. After that, App DB wins;
automatic contact rediscovery must not re-queue mirrored rows; silent lead-drawer
contact backfill is forbidden. Refresh is user-initiated (fill-blanks + mismatches).
The denormalized `qobrix_opportunity_mirror` does not change this — it is a
read cache, not SoT.

### D5 — Nurture loop

`demote_opportunity_to_lead` returns leads to **`nurturing`** (maps Qobrix
`asleep`). Won stays terminal; lost may recycle. `return_cycle_count` tracks
recycles. Demoted opportunities stay off the board even if Qobrix status is unchanged.

### D6 — Dedup across surfaces

`qualify_lead_v2` copies `external_qobrix_id` onto the new opportunity so Leads
and Pipeline merge on the same Qobrix id.

## Consequences

- Board EF fetches open pipeline stages by default; Won/Lost only when `include_closed`.
- Restricted viewers read live Qobrix as the caller (no MSA `owner==` override);
  unrestricted viewers may use the mirror. Silent 1k row caps are replaced by a
  named `BOARD_MAX_ROWS` ceiling with honest truncation.
- Hidden counters are mutually exclusive: `off_board` | `unmapped_stage` | `unqualified` | `hidden_by_scope` | `leads_surface`.
- **Transport-carried safety:** when a safety property lives only in the
  transport (per-user Qobrix token), changing the transport (live → shared
  mirror) silently removes it and no diff shows the loss. Prefer an explicit
  `viewerScope` argument + guardrail over comments claiming “reads as the
  caller.”
- Lead status enum adds `contacting`, `enquiry`, `nurturing`; `qualifying` deprecated.
- App opportunity `status` canonicalizes on `in_process` (legacy `open` migrated).
- Discovery EF `qobrix-stage-discovery` + `docs/qobrix/stage-mapping-discovery.md`
  validate tenant wire values before trusting seed row counts.
- Migrations: `20260827142245` (schema) → `20260827142302` (data) → `20260827195330` (RPCs + seed).
