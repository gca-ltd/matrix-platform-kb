# ADR-057: Datacore as the CY CRM analytics / scoring plane (partial supersede of ADR-004)

**Status**: Accepted  
**Date**: 2026-09-29  
**Scope**: Cyprus Qobrix CRM analytics for digital initiatives 004 (attribution + scoring), 005 (reservation slip), 006 (referral / reactivation).  
**Related**: [ADR-004](ADR-004.md), [ADR-009](ADR-009.md), [ADR-029](ADR-029.md), [ADR-035](ADR-035.md), [ADR-039](ADR-039.md), [intelligence-layer.md](../intelligence-layer.md), [security-model.md](../../platform/security-model.md), [app-catalog.md](../../platform/app-catalog.md)

## Context

ADR-004 made **Databricks** the platform DWH / ETL (medallion, future ML). That remains the listing / MLS path (`mls_2_0`, CDL gold).

For **CY CRM scoring** (lead conversion, reservation hazard, reactivation) we already run **Matrix Datacore** (`zcajghoohycimpubufsy`, `eu-central-1`): a Qobrix REST photograph in Postgres, curated `public.*`, read-only MCP. App-catalog noted this as “bypasses Databricks (ADR-004 pending)” without a superseding ADR.

Constraints that differ from listing DWH:

- Volume is tens of thousands of opportunities and hundreds of contracts — not a Spark workload.
- Personal data must stay in the EU region already used by Datacore.
- The team is three people; a second ML platform (MLflow on Databricks) is operating cost without lift.
- Digital Employees consume a 30s / ~9k-char MCP budget — scores must be **precomputed**.
- Datacore is a **service-harvested** photograph ([security-model.md](../../platform/security-model.md)): fine for unrestricted CORE / leadership analytics; **not** a broker-scoped CRM read path (initiative 1 “Alex” with Qobrix roles must not use it as SoR).

## Decision

1. **CRM analytics and mathematical scoring for CY live on Datacore**, not Databricks. ADR-004 / ADR-009 continue to govern **listing / MLS** medallion ETL into CDL.
2. Language-agnostic contract in schemas `history` (SCD2 + LogAudit), `metrics` (certified definitions + Wilson CI), `ml` (feature snapshots, labels, model versions, scores, eval, holdouts). R and/or Python batch jobs on the bastion write `ml.*`. Default hybrid: SQL metrics + Python stdlib scorers; R optional for survival/Bayes.
3. Nightly ingest stays Qobrix REST incremental. Local scoring after nightly is opt-in (`SCORE_AFTER_NIGHTLY=1`) and **never** calls DeepSeek. DeepSeek ranking remains on-demand, anonymized, and is **legacy** next to `public.score_current`.
4. MCP `datacore-mcp` v0.4 exposes certified metrics, benchmarks, math scores, and model cards over `public.*` only. No predict MCP.
5. After Qobrix is strangled by matrix-pipeline / MSA, `core` stays source-independent: swap the photograph, keep metric keys and `ml.*` tasks.

## Consequences

**Positive**

- Scoring, benchmarks, and CDTO tracker sit next to the data they measure, in EU Postgres.
- Model cards and Wilson intervals are queryable by agents without a second warehouse.
- Explicit security boundary: unrestricted grain only.

**Negative**

- Two analytical planes (Databricks listings vs Datacore CRM) until a later consolidation.
- SCD2 history starts 2026-09-29. A read-only probe on 2026-10-07 (few GETs, one request per second) found the Qobrix changes API no longer returns opportunity rows before 2026-04-04 (63 147 rows from that morning; nothing in October 2024; nothing before 2026-02-22). Datacore already holds the February–April copy. A two-year backfill would re-read stored rows and cannot reconstruct 2020–2025 stage or channel history. Do not arm it unless a later probe shows older rows.
- No MLflow; versioning is `ml.model_version` rows.

**Enrichment layer and review loop (2026-10-12)**

- Schema `enrich` parses facts that are already in the Qobrix photograph: inquiry text, a sha256 person key, repeat inquiries, handling times, and a candidate cancel timestamp. Every value carries method, source, confidence, and extractor version. `method = imputed` is not written into `ml.label` or `metrics.*`. There are no synthetic rows and no Qobrix writes.
- Agents read `public.lead_mart` and `public.enrichment_coverage`. Gaps and large score errors are `public.review_queue`. A person can answer by CSV into `ml.human_label`; only that human fact may fill a missing cancel date. E5 candidates stay sensitivity context.
- A minimal `properties` key pull (id, ref, legacy_id, owner, sale_rent, status) would be a one-off exception to ADR-004 / ADR-009: match keys only, not listing content. It is not armed. Until a person runs it, lead-to-property match stays at CRM URLs in the inquiry text and the rare manual link.

**Augmented training (2026-10-13)**

- The intake model may train on a mixture: real matured labels, imputed feature values, synthetic wins, and pseudo-labels for open leads. This is an owner decision. The earlier rule still holds for the record of truth: `ml.label` and `metrics.*` stay real outcomes, and every quality check compares predictions to real outcomes.
- All of the mixture lives in schema `aug` with provenance: which run, which method, which confidence, and for a synthetic row which two real wins it came from. `public.lead_mart_augmented` shows the fills and the challenger score next to the production one. `public.prediction_vs_outcome` keeps each prediction so it can be checked once the lead matures.
- A model trained this way starts as a challenger. `score/python/promote.py` makes it the champion only after it beats the current champion on real matured labels for three consecutive months, and reverts it after two consecutive losses. A lab sweep on 2026-10-13 found no augmentation that cleared this bar, so the champion was not changed.
- The nightly run only does this when `AUG_SCORE=1` is set, and a failure is logged and skipped. It does not call Qobrix or DeepSeek.

**Two-step gate (2026-10-23)**

- A refit is not installed because it trained. It becomes the frozen challenger only after a walk-forward on the six latest fully matured months: fit on outcomes known before the month, test on that month's real labels, pooled paired PR-AUC lower bound above zero, Brier no worse, mean probability within 30% of the real rate, at least 30 wins. It replaces a challenger that already has a stored backtest only when it also beats that backtest. The prospective clock then starts over.
- `promote.py` compares the two models' `ml.prediction_ledger` rows, and only where the label horizon ended after both predictions. Three consecutive passes promote. Revert applies only to a champion this rule installed, after two losses to the previous champion. `ml.label` is rebuilt nightly, so its `created_at` is not the maturity clock.
- `datacore-score-api` returns production scores for keys the caller already holds (`subject_key, p, algo, model_version_id, as_of`, at most 200). It does not list leads. An MSA server function may use it to decorate rows that function already read as the user. The MSA MCP server (ADR-058) does not call edge functions. The bearer stays on the server.

**Daily refresh (2026-10-23)**

- Refresh and replacement are different. Each night the same algorithm refits on real labels that have matured and becomes production only when it is not worse on the latest matured window (Brier no worse, paired AUC difference lower bound above −0.01). A failed check keeps yesterday's parameters. The production model id stays stable so the prediction ledger and the two-step gate keep one champion. Replacing the algorithm is still the two-step gate above.
- Two faster labels, both real `stage_event` outcomes with a 30-day horizon, let quality be checked on live leads in about a month. `intake_appt_30d` is an appointment within 30 days of an MQL created on or after 2026-02-22. E10 (walk-forward, rule fixed first) passed, and that model is in production. `reactivation_wake_30d` did not beat a constant rate, so it is not installed; sleeping briefs stay the 90-day experiment with the 20% holdout. `reservation_slip` with a handful of open reservations is a risk flag, not a probability.
- `public.score_health` shows the book, the recent real rate, prospective AUC and Brier on ledger rows that matured after the prediction, and the latest guard. `datacore-mcp` v0.6 serves the new tasks and that health row. Digital Employees remains the delivery surface. No daytime Qobrix pull.

**Not decided here:** outbound alert delivery, Qobrix write-back, broker-scoped Alex over Datacore, installing R on the bastion.
