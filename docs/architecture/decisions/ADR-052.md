# ADR-052: Two-source virtual dataset — Qobrix + App DB merge contract

**Status**: Accepted  
**Date**: 2026-09-02  
**Extends**: [ADR-051](ADR-051.md) (live Qobrix list read)  
**Scope**: Matrix Sales Automation — Leads, Pipeline, Contacts (per-user isolated);
listings catalog (tenant-shared) as a sibling authority model on the same paging
primitive

## Context

ADR-051 restored live Qobrix list reads under the caller's token. That left an
unresolved merge problem: MSA also holds App-DB rows (app-authored deals/leads,
MSA stage, contracts, copy-on-open twins). Six list surfaces implemented **five
different** merge models. Pipeline prefetched a bounded superset and sliced in
memory (wrong whenever the real set exceeded the ceiling). Leads `unshift`ed
app-authored rows onto page 1 only and undercounted the total. Contacts alone
had an exact combined count via `mergedListPaging.ts`.

A related data defect: bulk promotion (`retire_sa` Phase 3/4) inserted ~2,594
Qobrix-linked opportunities into `public.opportunities`, so
`local_opportunity_id` stopped meaning "user saved this here" and the Pipeline
elephant marker vanished. The local-only board leg also lacked
`external_qobrix_id IS NULL`, reopening the service-harvested-cache leak pattern
from [security-model.md](../../platform/security-model.md).

## Decision

### D1 — Two authority models, one paging primitive

| Model | Surfaces | Who may introduce App-DB rows |
|---|---|---|
| **Per-user isolated** | Leads, Opportunities/Pipeline, Contacts | Only rows with `external_qobrix_id IS NULL` that the caller owns under RLS. An App-DB copy of a Qobrix row is a **decoration**, not a second list row. |
| **Tenant-shared inventory** | Listings / Properties / Projects | App-DB copy is co-equal (steward sentinel ownership). May contribute on any page. |

Both use **bounded-overfetch merge** (D3). They differ only in which legs may
contribute rows.

### D2 — Security invariant (non-negotiable)

On per-user-isolated surfaces the App DB may:

- **Decorate or correct** a row the caller's own live Qobrix read returned
- **Introduce** only app-authored rows (`external_qobrix_id IS NULL`) under RLS

It may **never** introduce a Qobrix-sourced row the caller's own read did not
return. Enforce structurally:

1. App-DB list leg constructed inside the shared module with
   `external_qobrix_id IS NULL` baked in
2. Caller-visible id set is a **required** constructor argument (compile error
   if omitted) when intersecting overlay corrections
3. CI guardrail (`scripts/check_crm_live_read_path.mjs`) audits the module

Where the App DB **orders** a page (contract-derived `contracting` /
`payment`), Qobrix still owns **visibility**: hydrate candidates with the
caller's token via `id in [...]` and **drop** any id Qobrix does not return.

Aggregates follow the same rule: when Qobrix read is on, the App leg counts only
rows with no Qobrix id (required scope argument on `appAggregates` readers).

### D3 — Bounded-overfetch merge

Legs are disjoint by construction: `|U| = |Q| + |A|` (no dedup arithmetic).

For union window `[o, o+s)` with `o = (p-1)s`:

1. Fetch every **small** leg whole (app-authored + overlay correction set) —
   `nSmall` rows
2. Fetch Qobrix window `[max(0, o - nSmall), o + s)` as concurrent pages of ≤100
3. Merge on total order `(created, id)`, skip removed overlay ids
4. Slice exactly `[o, o+s)`
5. `total = qobrixCount - removed + added + nApp`

**Sufficiency:** a Qobrix row at union index `u` sits at Q index
`q = u - (small-leg rows ranked above it)`, so
`q ∈ [o - nSmall, o + s)`. Overfetch is bounded by `s + nSmall`, independent of
how large Qobrix grows.

**Total order required.** A single sort key (`created`) alone can duplicate or
drop rows when ties break differently across legs. Use `(created, id)` on both
legs via Qobrix `sort[]` array form.

**Offset drift accepted.** Live inserts while a broker is mid-scroll can repeat
or skip one row. Inherent to offset pagination. Cursor/keyset merge is the
migration path if drift becomes a real complaint (smaller overfetch `2s`, but
no jump-to-page).

### D4 — Pipeline per-stage routing

Board column is **not** a pure function of Qobrix `status`. `pickBoardStage`
also reads Qobrix `custom_sql` (sales seam) and `isMatchingReady(card)`. Status
inversion alone is insufficient.

| Requested stage | Pushable to Qobrix? | Who orders / pages |
|---|---|---|
| `viewing` | Exact status set | Qobrix |
| `won` / `lost` | Exact status set (lost terminal) | Qobrix |
| `qualification` / `matching` | OR-superset including `custom_sql == true` on leads-surface statuses; `isMatchingReady` refined in memory over that bounded set | Qobrix pages the superset |
| `contracting` / `payment` | Not pushable — App-DB contracts | App DB orders bounded set; Qobrix gates visibility by id intersection |
| `all` / `open` | Partial; membership is contract-dependent | Qobrix pages; overlay corrector supplies added/removed |

Build inversion from `effectiveStageMappings(overrides)` so tenant stage maps
are honoured. Delete `BOARD_MAX_ROWS` / `BOARD_DERIVE_CEILING` prefetch and
in-memory filter/sort/slice on the board path.

### D5 — Pushability matrix (Qobrix)

| Capability | Contract |
|---|---|
| `page` / `limit` | `limit ≤ 100` |
| `sort[]` | Array form; sortable keys: `created`, `status`, `source`, `enquiry_type`, `list_selling_price_to` (budget) |
| Search DSL | OR-grouping and boolean fields (e.g. `custom_sql`) verified; association paths allowed |
| Exact count | `limit=1` → `pagination.count` |
| Id hydration | `id ==` / `id in [...]` chunks ≤ 100 |
| **Not pushable** | MSA-derived stage, `isMatchingReady` split, contact/area/campaign sort, app-authored rows, contract-derived columns |

Pipeline must restrict sortable headers to the Qobrix-sortable set (mirror
`LEADS_LIVE_SORT_KEYS`). Trust the server page — no client re-filter/re-sort of
board results.

### D6 — Shared module for per-user surfaces

One module (extend `src/lib/sales/mergedListPaging.ts` + EF-side twin) owns
paging, totals, and invariant enforcement. Per-surface **spec** supplies:
upstream resource, search builder, sortable-key allowlist, row mapper, optional
overlay corrector.

Migrate in order of blast radius: **Pipeline → Leads → Contacts**. Listing
catalog is a deferred sibling on the same paging core with the tenant-shared
model. Agents/Developers stay single-source live Qobrix; pass explicit `sort[]`.

### D7 — Saved-here marker and inert promotion cleanup

Delete inert auto-promoted opportunities (no user footprint) from
`public.opportunities` after shadow backup. Keep app-authored rows and any row
with contracts, stage work, shortlist, emails, qualification, MSA stage, etc.
Emit an explicit saved/materialised signal from the board row mapper; stop
inferring from `local_opportunity_id` alone. User-facing show/hide of
Qobrix-only rows is [ADR-054](ADR-054.md) (`saved_here_only` board mode).

### D8 — Rejected alternatives

- **Block concatenation** — exact but not globally ordered (Leads today)
- **Cursor/keyset merge** — preferred long-term; forbids jump-to-page today
- **Binary-search offset split** — ~9 sequential upstream RTTs; rejected on latency
- **Re-materialise a mirror** — forbidden by ADR-051 / security-model
- **Write-through to Qobrix on create** — strategic direction to drive `nSmall → 0`

## Consequences

- List correctness no longer depends on a silent prefetch ceiling
- Overlay size after cleanup (~535 Qobrix-linked keepers + ~334 app-authored)
  keeps overfetch tractable
- Dashboard/funnel/win-loss/scorecard App-leg counts drop once (correcting
  double-count of promoted rows); release note must state the expected change
- Contract-derived columns remain App-DB-ordered; invariant holds via Qobrix
  intersection
- Offset drift remains an accepted trade until cursors
