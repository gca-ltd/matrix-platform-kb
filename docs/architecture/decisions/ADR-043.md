# ADR-043: Person-keyed MCP grants and OAuth consent binding

**Status**: Accepted  
**Date**: 2026-08-25  
**Depends on**: [ADR-040](ADR-040.md), [ADR-041](ADR-041.md)  
**Scope**: `matrix-digital-employees` MCP client (`oauth_user` / Mode D)

## Context

Digital Employees calls remote MCP tools (notably Qobrix CRM) under an explicit
principal. Tokens live in `mcp_principal_tokens` keyed by
`(server_id, principal_kind, principal_id)`.

Two defects stacked in production (2026-08-22 → 25):

1. **Wrong human.** A Teams group-thread OAuth state was created for a
   `channel_identity` principal. Whoever completed the browser consent bound
   *their* Qobrix account to *that* principal. Sergey Seregin's Teams identity
   held Anton Bulakh's CRM grant; CRM questions in Teams answered with the wrong
   person's scope.
2. **No recovery + dishonest reply.** `channel_identities.sso_user_id` was never
   written, so Teams callers stayed on `channel_identity`. Sign-in entry points
   only minted `sso_user` grants. When the mis-bound token was rejected inside an
   HTTP 200 tool result (`Unauthorized`), the platform treated it as an ordinary
   tool string; empty `tool_guidance` let the model invent "CRM is warming up".

The memory layer already unifies humans by channel-asserted email via
`principals` (`UNIQUE (tenant_id, email)`) and `channel_identities.principal_id`.
The token layer did not.

## Decision

### D1 — Key channel OAuth grants on the email-verified person

When a channel caller has a channel-asserted email, resolve/create
`principals.id` and store MCP tokens as:

| `principal_kind` | `principal_id` |
|------------------|----------------|
| `person` | `principals.id` |

Prefer a linked `sso_user_id` when present (unchanged). Signed-in Playground
sessions stay `sso_user` so existing grants keep working. One `person` grant
covers every Teams thread for that email.

### D2 — Never post OAuth links into group threads

On `AuthRequiredError`, mint a sign-in URL only in a private thread. In a group
thread, tell the user to message the employee privately. Group-posted authorize
URLs are how defect 1 happened.

### D3 — Consent binding via `auth_config.identityProbe`

After the OAuth callback stores a grant, optionally call
`identityProbe.tool` and require `identityProbe.emailPath` to match
`mcp_oauth_states.expected_email`. On mismatch, delete the grant and fail with
"Wrong account". Qobrix: `qobrix_whoami` → `profile.user.username`.

### D4 — Auth-shaped tool results are `auth_required`

For `oauth_user` / `oauth_service`, an `isError` tool body matching auth patterns
triggers a single forced refresh; a second failure clears the token and raises
`AuthRequiredError`. The default `tool_guidance` forbids inventing a transient
cause.

## Consequences

- Teams users must re-authorize once under the `person` key after containment
  deletes mis-bound `channel_identity` grants.
- Operators configuring a new `oauth_user` server that returns a stable email in
  a whoami-style tool should set `identityProbe` to prevent cross-account binds.
- Playground and Teams grants for the same human remain separate until/unless
  `sso_user_id` is linked on the channel identity.

## Alternatives considered

- **Populate `sso_user_id` by email match to SSO.** Rejected as primary keying:
  requires a live SSO directory lookup from the channel path and still leaves
  unlinked callers without a grant key. Kept as a future enhancement on top of
  `person`.
- **Synthetic tools / `AUTH_REQUIRED:` prefixes.** Rejected earlier in ADR-040;
  this ADR keeps the real MCP catalogue and routes auth through
  `AuthRequiredError` + human-readable tool results.
