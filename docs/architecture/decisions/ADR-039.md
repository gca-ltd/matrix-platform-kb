# ADR-039: MCP reference architecture — the Qobrix stack

**Status**: Accepted  
**Date**: 2026-08-21  
**Supersedes**: [ADR-032](ADR-032.md), [ADR-038](ADR-038.md) as the *platform* MCP reference (those ADRs are Obsolete; ITSM MCP remains in-tree but is no longer normative)  
**Extends**: [ADR-011](ADR-011.md) (ES256 SSO direction), MCP specification 2026-07-28 authorization  
**Scope**: Public Resource Server [`qobrix-crm-mcp`](https://github.com/gca-ltd/qobrix-crm-mcp) + proprietary Authorization Server [`qobrix-crm-mcp-oauth`](https://github.com/gca-ltd/qobrix-crm-mcp-oauth); live oauth_user endpoint `https://intranet.sharpsir.group/qobrix-crm/mcp`

## Context

The platform needed a production-proven MCP server that third-party hosts (Claude.ai, Dust.tt, Cursor) and first-party Matrix agents can both connect to. The ITSM MCP (ADR-032/038) was an app-local experiment and is **obsolete** as a platform pattern. The Qobrix CRM MCP stack shipped four auth modes that have been validated in production; it is the reference for every new Matrix MCP *server* and for how Digital Employees' *client* maps auth modes.

## Decision

### D1 — Canonical mode taxonomy (from `qobrix-crm-mcp` `src/modes.ts`)

| Mode | Env | Client presents | Who holds user identity |
|------|-----|-----------------|-------------------------|
| **A** | stdio + env | process env `X-Api-*` | Shared service key (local only) |
| **B** | HTTP + `headers` | Per-request `X-Api-User` / `X-Api-Key` | Caller (trusted network) |
| **C** | HTTP + `oauth` | **Nothing** — server returns `/connect` in tool results | MCP session vault + paired AS |
| **D** | HTTP + `oauth_user` | `Authorization: Bearer` after PRM + OAuth | Client drives OAuth; AS vault |

stdio is irrelevant to Edge Function clients (no stdio). api_key and oauth_user are first-class.

### D2 — Split RS / AS

- **Resource Server** (`qobrix-crm-mcp`): open-core, Streamable HTTP, 64 read-only tools, RFC 9728 Protected Resource Metadata with path-aware well-knowns (`src/oauth-rs.ts`).
- **Authorization Server** (`qobrix-crm-mcp-oauth`): proprietary — login + 2FA + consent, DCR, PKCE S256, opaque audience-bound tokens, AES-256-GCM credential vault, `/introspect` with shared secret returning Qobrix API credentials.

Tokens are **not** self-contained JWTs. The RS validates via introspection; positive cache ≤ 30s. Audience (`aud`) must equal `QOBRIX_MCP_RESOURCE_URL` (RFC 8707).

### D3 — Per-user vault + revocation contract

On successful login the AS mints a Qobrix API key and stores `{ sub, qobrixApiUser, qobrixApiKey, … }` encrypted.  
`sub = sha256(apiUrl|userUuid)`.

When the vault entry is deleted (disconnect / revoke), introspection returns:

```json
{ "active": false, "error": "credentials_revoked" }
```

The RS then 401s. **Clients must treat this as `auth_required` and mint/re-show a real authorize URL** — never invent one. This is the contract Digital Employees depends on for dead-upstream-credential recovery.

### D4 — Known deltas vs MCP 2026-07-28 (remediation backlog)

The AS predates the July 2026 revision:

| SEP | Requirement | Qobrix AS today |
|-----|-------------|-----------------|
| 2468 | `iss` on authorization response | Not emitted |
| 2352 | Issuer-bound client credentials | Not recorded |
| 837 | `application_type` at DCR | Not sent |
| 2207 | `offline_access` for refresh | Refresh works without the scope name |
| 2350 | Scope accumulation | Single scope `qobrix:read` |
| 2351 | Path-aware `.well-known` | **Already correct** |

DCR is used; Client ID Metadata Documents (CIMD) are not yet offered. Clients **must be tolerant**: validate `iss` when present; fall back to DCR when CIMD is absent.

## Consequences

- New Matrix MCP servers copy this RS/AS split and mode taxonomy.
- ITSM MCP docs remain historical; do not cite ADR-032/038 for greenfield work.
- Property-side `matrix-mcp` (shared HS256 bearer) is **legacy / non-compliant** for remote MCP and must not be presented as the platform pattern (see `docs/platform/matrix-mcp-server.md`).
- Hardening the Qobrix AS for SEPs 2468/837/2352/2207 is a separable follow-up.
