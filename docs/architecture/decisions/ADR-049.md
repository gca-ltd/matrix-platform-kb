# ADR-049: HU listings MCP on Supabase Edge Function (Mode B)

**Status**: Accepted  
**Date**: 2026-08-31 (amended 2026-09-02, 2026-09-29)  
**Scope**: HU listings MCP backend in the Storefront repo [`gca-ltd/matrix-storefront-2.0-hungary`](https://github.com/gca-ltd/matrix-storefront-2.0-hungary) (`supabase/functions/`, `supabase/migrations/`, runbook `docs/mcp/README.md`), Supabase project `bpaxqtxaysolzaeguwvg`

## Context

Digital Employees needs semantic access to Hungarian property listings published on `sothebys-realty.hu`. Source data lives in the HU website Supabase project (`bpaxqtxaysolzaeguwvg`, internal name `hu-website`). The Qobrix CRM MCP pattern (ADR-039) is the platform reference for protected, per-user data, but HU listings are **public marketing copy** already on the website. The consumer is server-to-server (Digital Employees edge functions calling an MCP Resource Server). Lead capture for MSA-HU is a separate write path.

Requirements:

1. Qwen embeddings at 1024 dimensions (Hugging Face Inference Providers `qwen3-embedding-8b` preferred; DashScope `text-embedding-v4` fallback).
2. Hybrid vector + full-text search with hard SQL filters (EUR price, bedrooms, city, sale vs rent, visibility).
3. Read-only MCP tools for catalogue discovery; write MCP tools for lead / viewing capture.
4. Portable to future prod HU Supabase project (clone → cutover).

## Decision

### D1 — Two MCP servers: read catalogue vs write leads

- **`hu-properties-mcp`** — six read-only tools over hybrid search (`match_properties_v2`).
- **`hu-leads-mcp`** — two write tools (`hu_capture_lead`, `hu_request_viewing`) that persist to `lead_intents` with an MSA-HU push adapter stub.
- Embedding computation stays a **non-MCP** cron Edge Function (`embed-properties`) plus `embedding_queue` triggers.

Search and write are split by server, bearer token, and Digital Employees policy (Allow vs Require approval).

### D2 — Supabase Edge Function RS with Mode B bearer

Deploy both MCP servers as stateless JSON-RPC 2.0 Streamable HTTP Edge Functions in the **same** Supabase project as the listings data. Authenticate with service bearers (`HU_PROPERTIES_MCP_TOKEN`, `HU_LEADS_MCP_TOKEN`, `auth_mode: api_key` in Digital Employees). No Authorization Server — catalogue data is public and the caller is trusted infrastructure; lead writes are gated by DE approval policy + consent flag.

### D3 — Embeddings in HU Postgres, not Digital Employees knowledge

Store vectors in `property_embeddings` / `development_embeddings` (`extensions.vector(1024)`) in `bpaxqtxaysolzaeguwvg`. Do **not** ingest listings into Digital Employees `knowledge_chunks` (1536-dim OpenAI embeddings, no SQL predicates). Brand FAQ remains in native DE RAG.

### D4 — Embedding provider contract

Prefer Hugging Face router (`HF_TOKEN` → Scaleway `qwen3-embedding-8b`, `dimensions: 1024`). Fall back to DashScope international compatible-mode when `DASHSCOPE_API_KEY` is set instead. Batch size ≤ 10. Query embeddings use Qwen instruct prefix; document embeddings do not. Query results are cached in `query_embedding_cache`.

### D5 — Served slice, EUR algebra, slug addressing

- Default catalogue scope: `is_visible = true AND status IN ('For Sale','For Rent')` (~129 listings).
- All price filters are in **EUR**. `properties.price_eur` is maintained by trigger from `fx_rates` (manual HUF→EUR rate).
- `transaction_type` (`sale` | `rent`) keeps rental monthly prices out of sale budgets.
- Public URLs use `slug` (`/properties/{slug}`, `/en/properties/{slug}`); `property_key` is the display Listing ID only.
- FTS uses `simple` + `unaccent` over bilingual `search_text` (not language-specific configs over mostly-English copy).
- Empty hard-filter results may auto-relax once each: drop district → widen price ±20% → drop min_bedrooms; response echoes `applied_filters` + `relaxed`.

### D6 — Source lives in the Storefront repo until listings move to an MLS (amended 2026-09-29)

The stack was first built in a separate local-only repo (`/home/bitnami/supabase`) to stay out of the
Lovable co-authored Storefront tree. It now lives in `gca-ltd/matrix-storefront-2.0-hungary` as an
integral part of the Storefront backend (commit `611f3de`): same Supabase project, same deploy path
(`supabase functions deploy`, not github-watcher), `verify_jwt = false` pinned in `supabase/config.toml`,
Cursor-owned per the repo's `AGENTS.md` / `.lovable/instructions.md`. Deployed functions were verified
byte-identical to the moved source, so no redeploy and no behaviour change.

When listing management is extracted from the Storefront into a dedicated MLS, the MCP stack (functions,
embeddings, `match_properties_v2`) moves with the listing tables. Tool names stay stable across that move.

## Deliberate divergence from ADR-039

ADR-039 normative pattern: Node + `@modelcontextprotocol/sdk` on pm2 behind Apache, RS/AS split, per-user OAuth for protected CRM data.

We diverge because:

1. **Co-location** — MCP tools query pgvector in the same Postgres; a Node RS on the intranet VM would hold a service-role key and add a network hop per tool call.
2. **Auth model** — Public listings, single server caller (Digital Employees); Mode B bearer matches ADR-048 (Charts) class, not Qobrix Mode D.
3. **Portability** — EF deploys with `supabase functions deploy` on project cutover; no pm2 slot on an already crowded intranet VM.
4. **Write path** — Lead capture is still Mode B (service caller) but separate token + DE approval; MSA-HU adapter is stubbed until CRM intake exists.

If HU listings later expose non-public fields or per-user authorization, migrate RS to ADR-039 Node stack **without changing tool names**.

## Consequences

- Digital Employees registers **two** `api_key` MCP connectors; search tools Allow, lead tools Require approval.
- Operator sets `HF_TOKEN` (or `DASHSCOPE_API_KEY`), `HU_PROPERTIES_MCP_TOKEN`, `HU_LEADS_MCP_TOKEN`, `EMBED_SCHEDULER_SECRET` on HU project.
- Full embed ~520 rows (257 properties × 2 langs + developments).
- Manual `fx_rates` must stay roughly current or sale filters on HUF-priced rows drift.
- Eval harness: `scripts/mcp/eval-search.mjs` (boundary + URL + latency).
- WhatsApp is a constrained delivery surface: it does not render Markdown tables and public HU property URLs currently expose only generic Open Graph metadata, so rich catalogue replies on WhatsApp require platform-side image messages and/or message splitting rather than relying on URL preview cards.
