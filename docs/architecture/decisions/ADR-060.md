# ADR-060: Progressive tool discovery

**Status:** Accepted
**Date:** 2026-10-05
**Scope:** Digital Employees tool selection
**Related:** [performance.md](../../platform/performance.md);
[mcp/README.md](../../platform/mcp/README.md);
[agent-guidance.md](../../platform/mcp/agent-guidance.md)

## Context

Digital Employees talks to a handful of MCP servers and under two hundred tools. The catalogue is still small enough to rank in one SQL call, and large enough that putting every schema in the model request wastes the window and the prompt cache.

The previous turn ranked every allowed tool once, from the raw last user message, and always filled 12 slots. A tool found later was still called through a wrapper. Scores in the tail were far below the tools the model actually used. Follow-ups such as "for these two" ranked against a short message with no memory of the previous reply.

A later platform gateway can sit in front of hundreds of servers. The same four steps have to work there: one registry, find the server, find the tool, then call it. This decision puts those steps in Digital Employees now, using the mechanism each model API already documents.

## Decision

1. The registry stays `mcp_servers`, `mcp_tools`, `mcp_tool_defaults`, and `mcp_tool_policies`. A tool is callable only when its policy is Allow or Ask.
2. Ranking text is the latest user message, the head of the previous assistant reply, and the names of recently used tools. No extra model call.
3. Server cards (name, instructions, usage notes, tool names) are embedded on `mcp_servers`. `rank_employee_servers` picks the closest servers that clear the relevance floor. `rank_employee_tools` then ranks only inside those servers. Until server embeddings exist, every allowed server is ranked.
4. Loaded tools are the recent ones (up to 5) plus ranked tools at or above 0.25, stopping at the first score gap of 0.12, capped at 12. Below the floor, only the discovery tools load.
5. A tool found by `tool_search` is called directly on the next step.
   - Compatible providers (the Lovable gateway, DeepSeek, and other workspace endpoints) register every allowed tool and send the loaded set through `activeTools`. Search hits are appended, so the earlier order stays stable.
   - The native Messages API sends every allowed tool. Tools that are not loaded set `defer_loading`. `tool_search` returns tool-reference blocks, which the API expands inline and leaves the cached prefix untouched. A deferred tool carries no cache breakpoint. `tool_search`, `answer_ready`, and the loaded tools stay eager.
   - `tool_invoke` stays as a fallback on both paths.
6. Models that reject a forced tool call (`tool_choice` required) are marked `tool_choice_required: false` in the catalog. Their tool steps send `auto` and the tool phase ends on `answer_ready` or on a step that writes the reply with no tool call. Claude Fable 5.1, Claude Mythos 5.1, and Gemini 3.1 Pro are marked this way. Gemini Flash on the same gateway accepts stream usage, so that stays on.
7. MCP tools that return JSON accept an optional `fields` argument, a list of dotted paths. The executor trims the result before the model sees it and says the result was trimmed. Omitting `fields` returns the result unchanged.
8. `prep` records `selectionRecall`, `discoveryHops`, and `schemaChars`. Changing the sent tool list changes the request prefix, so compare `cached_input_tokens` as well.

## Consequences

- A turn with a weak match no longer spends the window on twelve unrelated schemas.
- A follow-up ranks against the previous reply and the tools just used.
- Search is rarer when the right tool was loaded, and a search hit is a normal call on the next step.
- Server-card fills do not bump `tenant_config_epoch`.
- The same steps can move to a platform gateway later without a second registry. That gateway is not built here.
