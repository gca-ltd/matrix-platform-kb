# ADR-040: Digital Employees MCP client contract

**Status**: Accepted  
**Date**: 2026-08-21  
**Depends on**: [ADR-039](ADR-039.md) (Qobrix stack as server reference)  
**Scope**: `gca-ltd/matrix-digital-employees` — `supabase/functions/_shared/mcp/`, `mcp-admin`, `mcp-oauth` (app DB `mihslqjjclbrqelnjjpb`)

## Context

Digital Employees is an MCP *client*: it registers remote MCP servers per tenant and exposes selected tools to agents. The previous `tool_*` layer could not express Qobrix api_key (multi-header API keys) or the retired signed-header path (server-managed connect URL), used plaintext tokens, keyed OAuth by a fuzzy `userId`, and ran approvals as the approver instead of the original principal.

## Decision

### D1 — Five client auth modes (map to ADR-039)

| Client `auth_mode` | Qobrix mode | Behaviour |
|--------------------|-------------|-----------|
| `none` | — | No credential |
| `api_key` | **B** | Arbitrary header set from encrypted secrets / env `secret_ref` |
| `oauth_user` | **C** | No client credential; detect connect URL in tool results → `AuthRequired` |
| `oauth_user` | **D** | Per-principal OAuth 2.1 + PKCE; PRM discovery; tokens encrypted |
| `oauth_service` | — | Client-credentials for machine identity |

stdio (stdio) is unsupported in Edge Functions.

### D2 — Explicit principal

```ts
type McpPrincipal =
  | { kind: 'sso_user'; id: string }
  | { kind: 'channel_identity'; id: string; ssoUserId: string | null }
  | { kind: 'service'; id: string };
```

- Tokens and `mcp_tool_calls` rows are keyed by principal.
- `service` principals may only use `none` / `api_key` / `oauth_service` — never personal OAuth.
- Approvals **replay as the original principal**, not the approver.

### D3 — Protocol and storage

- Prefer `MCP-Protocol-Version: 2026-07-28`, fall back once to `2025-06-18`.
- Session id optional; reused for the whole run.
- Secrets and OAuth tokens: AES-256-GCM (`MCP_ENC_KEY`).
- OAuth client registrations stored per `(server_id, issuer)` (SEP-2352).
- Canonical callback: `…/functions/v1/mcp-oauth/callback`. Legacy `…/tools-oauth` remains a shim because that URL is an external allow-list contract (Qobrix `QOBRIX_OAUTH_REDIRECT_ALLOWLIST`).

### D4 — Agent-facing auth (superseded for oauth_user)

~~Sign-in URLs are returned as plain text tool results prefixed with `AUTH_REQUIRED:`.~~

**Superseded by [ADR-041](ADR-041.md)** for `oauth_user` (Qobrix the retired signed-header path):
the server owns the connect URL in tool results; the client does not mint OAuth
links or add `AUTH_REQUIRED:` prose. `oauth_user` servers still use
`mcp-oauth` client OAuth.

## Consequences

- Schema lives in `mcp_*` tables (backfilled from `tool_*`).
- Admin UI rebuilt around the five auth modes (`src/components/mcp/*`).
- Edge functions: `mcp-admin` (registry/policy/approvals), `mcp-oauth` (callback + start/status/disconnect); `tools-api` / `tools-oauth` are shims during cutover.
- Frontend ships via github-watcher on push to `main`.

### Backend delivery on Lovable Cloud (2026-08-21)

The app DB is Lovable Cloud managed, so Cursor cannot deploy to it: `supabase db
push`, `supabase functions deploy` and the Management API all return **403** for
the platform account. This is a property of Lovable Cloud, not a permissions bug,
and it applies to every Lovable Cloud app — not just this one.

Delivery therefore runs through the **Lovable MCP server** (`mcp.lovable.dev`),
which drives Lovable's own agent against the synced repo:

| Step | Mechanism |
|---|---|
| Verify schema / row counts | `query_database` (argument is `sql`) |
| Apply a committed migration | `send_message`, instructing verbatim execution |
| Deploy named edge functions | `send_message` |
| Backend secrets (e.g. `MCP_ENC_KEY`) | Operator only, via Lovable → Project Settings → Secrets. No MCP tool exists. |

Ordering is load-bearing: **migration first, functions second.**
`_shared/agent-tools.ts` reads only `mcp_*` and swallows query errors, so
functions deployed against a missing schema silently strip every employee's tools
rather than failing loudly.

Two consequences to plan for. Lovable re-records applied SQL under its own
`supabase_migrations` version and writes its own migration file, so the same DDL
lands in two files — keep the recorded one. And `verify_jwt` can only be set in
`supabase/config.toml`, since there is no CLI flag to pass; the SSO-verifying
functions declare `false` there.

Cutover completed 2026-08-21: migration applied and verified (10 `mcp_*` tables,
20 tenant policies, credential tables service-role only, OAuth client and
per-user grants carried over), all 13 MCP-dependent functions deployed,
`MCP_ENC_KEY` set, and `USE_MCP_ADMIN = true` shipped. Verified live against the
deployed build: registry and tool list render from `mcp-admin`, policy writes
persist, `mcp-oauth status` reports the carried-over connection as connected, and
no `tools-api` call is made. The legacy `tools-api` / `tools-oauth` branches and
the `tool_*` tables stay in place for one release as the rollback lever.

Follow-up: the migration backfilled `mcp_oauth_clients.client_secret_enc` with a
`legacy:` prefix over the plaintext value from `tool_server_oauth_clients`, which
`decryptSecret` unwraps transparently — that is what keeps the existing grant
refreshable instead of forcing re-consent. It also means those secrets are still
plaintext at rest (no worse than the legacy table they came from). Re-encrypt
opportunistically on the next OAuth start, in the `existing` branch of
`_shared/mcp/auth/oauth/client.ts`, and drop the `legacy:` escape hatch from
`decryptSecret` once no prefixed rows remain.

2026-08-22: removed `bootstrapSignInTools` — the agent tool surface is exactly
what each server publishes; auth links flow via `AUTH_REQUIRED` tool results and
model relay (see `docs/platform/mcp-client.md` § Agent contract). Chat sign-in
card (9990367) reverted.
