# ADR-046: Qobrix broker → SSO identity is a persisted map, not a per-request derivation

**Status**: Accepted  
**Date**: 2026-08-28  
**Depends on**: ADR-044 (Qobrix surface partition + copy-on-write), `admin-ad-users` identity contract  
**Scope**: `matrix-sales-automation` App DB (`rpoeezssicpzexarmwqq`); SSO `admin-ad-users`

## Context

`backfill-opportunity-from-qobrix` materialises a Qobrix opportunity into the App
DB when a broker opens it from the board. Until now it hardcoded
`x_assigned_user_id: null`, on the reasoning that "a Qobrix user id is not an SSO
uuid". That is true of the *id* but not of the *person*: the Qobrix user record
carries a login address that resolves to an SSO account for most of the roster.

The consequence was that every imported deal landed ownerless. Cards read
"Unassigned", self-scope visibility could not work, and Reassign had no
from-value. The display-only Qobrix owner hint shipped earlier that day made the
symptom legible but did not fix ownership.

MSA's App DB and SSO are different Supabase projects, so `auth.users` cannot be
joined. The only bridge is the SSO `admin-ad-users` edge function, which emits
`supabaseUserId` (= `auth.users.id` = JWT `sub`) — the value the App DB actually
stores in `x_assigned_user_id`.

Measured against the SSO directory, the 78 Qobrix users resolve as: 40 by exact
email, 2 by email local part only (`epestova@cyprus-sothebysrealty.com` vs
`epestova@sothebysrealty-cyprus.com`), 2 by display name only (a broker who
changed surname still signs into Qobrix under the old local part), and 34 not at
all — mostly service accounts and departed staff.

## Decision

### D1 — Persist the mapping in the App DB

`public.qobrix_user_sso_map` (tenant-scoped, keyed `(tenant_id, qobrix_user_id)`)
stores the resolved `sso_user_id` plus the evidence: both emails, both display
names, and the `match_method`.

The alternative — resolving through the directory on each import — was rejected
for two reasons. It costs a cross-project round trip on a latency-sensitive path,
and more importantly it leaves nowhere to record a human's judgement about an
ambiguous match.

### D2 — Only exact-email and human-confirmed matches may own a deal

`match_method` is one of `exact_email | localpart | name | manual | none`. The
import path reads through `lookupConfirmedSub`, which returns a subject **only**
for a row with `confirmed = true` — set automatically for `exact_email`, and by
an admin for `manual`.

Local-part and display-name matches are stored unconfirmed and surfaced in
Administration → Qobrix Ops for review. Silently binding them would mean guessing
at ownership: Qobrix logins drift from SSO ones, and a wrong owner is worse than
no owner because it removes the deal from everyone else's self-scope board.

A key that resolves to two different people is treated as no match at all rather
than first-wins.

### D3 — The map is built by an admin sweep, not lazily

`admin-ad-users` is gated by `requireAdmin` (global scope), so an ordinary broker
opening a card cannot resolve their own identity — the call would 403. The
`qobrix-sso-map-sync` edge function therefore rebuilds the whole map as an admin
action, forwarding the caller's bearer token, and the import path does a plain
table lookup afterwards.

The sweep never overwrites a row whose `confirmed_by` is set: a human decision
outranks a later re-derivation.

### D4 — Assignment fills blanks only

`backfill_opportunity_assignees_from_qobrix_map(tenant)` runs at the end of each
sweep and fills `x_assigned_user_id` on Qobrix-linked opportunities that have
none. Existing assignees are never touched — once MSA has an owner, MSA is the
source of truth and Reassign is the only thing that may change it. The same
fill-blank rule applies on the refresh path, so a deal imported before its broker
was mapped picks up an owner later.

The Acme demo tenant is unaffected: the map is tenant-scoped, so real Sharp SIR
brokers cannot be assigned to demo data.

### D5 — Failed directory reads never erase bindings

`qobrix-sso-map-sync` treats a directory response with no provisioned
`supabaseUserId` rows as unavailable and returns an error without writing the map.
If a partial response cannot match a broker that already has a subject, that
existing binding is preserved. A transient SSO bridge failure must not turn every
deal into an unassigned deal.

### D6 — CRM contact ownership uses the SSO subject

`contacts.assigned_to` is a text column for compatibility, but its CRM ownership
value is the SSO JWT `sub`, just like `opportunities.x_assigned_user_id`.
Legacy imports that stored an app `agents.id` or a raw Qobrix user id are
normalized through this map. The `agents` shadow table remains available for
Qobrix listing-agent display and is not an ownership key.

Contracts copied from the Qobrix mirror retain their Qobrix `assigned_to` and
`commission_to` values. Their display names are resolved through the Qobrix
shadow directory; they do not use the opportunity's SSO assignee column.

Qobrix listings use the existing `agents` shadow directory. When
`agent`/`salesperson` is absent, the mirror uses project `assigned_to` or the
Qobrix `created_by` user as the listing-agent source. This is display metadata,
not CRM ownership.

## Consequences

- An assigned deal becomes visible to that broker under self scope and drops off
  other self-scope users' boards. This is the intended behaviour and the reason
  the confirmation bar is set where it is.
- Brokers with no SSO account (service accounts, departed staff) keep landing
  unassigned, with the read-only Qobrix owner hint as before.
- Qobrix remains read-only. Nothing here writes back, and the SSO `sub` stays the
  canonical assignee identity — the map only translates into it.
- A Qobrix broker without a confirmed SSO account remains unassigned in CRM
  surfaces; the source owner may still be shown as a display-only hint.
